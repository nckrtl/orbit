# Feature plan

Issue: ORB-132
Review verdict: PASS

## Outcome

An issue proof plan can add one attempt-local `app-prod-2` Node to discovery and proof while the shared topology snapshot and standard three-Node flow stay unchanged.

## Code boundaries

In:
- Declaration, addressing, and persisted topology identity: extend `apps/e2e/app/E2E/Value/ProofPlan.php`, `TopologyEndState.php`, `TopologyRecipe.php`, `TopologyTarget.php`, `FeatureTopology.php`, `ProofResult.php`, `ProofFixtures.php`, and the new typed extension/construction-input values beside them. The optional normalized plan field is `"extension": "app-prod"`; it selects the physical Node key `app-prod-2`, Incus address `.13`, WireGuard address `10.44.0.4`, and forces `mutates: true`. No extension field preserves the current serialized plan and fingerprint.
- Plan loading and mixed-source construction: update `apps/e2e/app/E2E/ProofPlanFile.php`, `TopologyAcquirer.php`, `TopologyProofRunner.php`, `HostCapacity.php`, `DiscoveryGuestPreparer.php`, `IncusNetworkLifecycle.php`, `app/Providers/AppServiceProvider.php`, and a shared `apps/e2e/app/E2E/IssueTopologyConstructor.php`. The constructor reserves the selected recipe size before mutation, copies only the three registered Nodes from the pinned generation, creates only `app-prod-2` from the configured generic image, records the observed image fingerprint and full intended inventory, and rolls that inventory back on failure. `topology:acquire` reads the active issue plan when present before it creates the discovery lease or any Incus resource. `TopologyAcquirerTest.php` exercises extended discovery construction and proves that discovery and proof retain distinct attempt identities, VM names, addresses, and inventories without adopting either attempt's resources.
- Convergence and verification: make `apps/e2e/app/E2E/TopologyConverger.php`, `TopologyVerifier.php`, `WorktreeSynchronizer.php`, `ProofFixtureStager.php`, `ProofInputManifestBuilder.php`, `ProofEquivalenceEvaluator.php`, `resources/guest/converge-app-prod-internal-tls.sh`, `resources/guest/converge-sample-app.sh`, and `resources/guest/verify-topology.sh` operate on physical recipe Nodes. Provision and converge both app-prod Nodes through the existing product command while preserving the supported `e2e-dev` AppInstance on `app-dev` and its existing app-dev hydration path; neither app-prod Node contains an AppInstance. Verify `app-prod-2` network identity, app-prod role, PHP-FPM, Caddy, and fixture/runtime execution without changing product placement or routing behavior.
- Command targeting, retained evidence, and exact cleanup: update `apps/e2e/app/Console/Commands/Topology/{Acquire,Exec,Shell}.php`, `apps/e2e/app/E2E/Value/ProofInputManifest.php`, `IssueState.php`, `TopologyReleaser.php`, and `TopologySnapshotPromoter.php`. Commands and proof actions accept only physical keys from the recorded recipe; topology and proof-input schemas bind the extension, source generation, image alias and fingerprint, ordered four-Node identities, and action results; equivalence and promotion revalidate them; release uses the persisted inventory and keeps the lease after an ownership conflict or partial failure.
- Public harness and closeout guidance: update `bin/e2e-topology`, `.agents/skills/developing-features/SKILL.md`, `.agents/skills/merging-pull-requests/SKILL.md`, and `apps/e2e/tests/Feature/Configuration/AgentRoleContractTest.php`. The developer writes the extended proof declaration before acquisition, and closeout treats its normalized mutating proof as refresh-only, records the required handoff identities, and releases proof and discovery only after refresh succeeds.
- Focused coverage stays in the issue-named tests: `apps/e2e/tests/Unit/E2E/Value/{ProofPlan,TopologyRecipe,FeatureTopology,ProofEvidenceValue}Test.php`, `apps/e2e/tests/Unit/E2E/{HostCapacity,TopologyAcquirer,TopologyConverger,TopologyVerifier,TopologyProofRunner,ProofFixtureStager,ProofFixtureContract,ProofFixtureShellContract,ProofInputManifestBuilder,ProofEquivalenceEvaluator,TopologyReleaser,TopologySnapshotPromoter}Test.php`, and `apps/e2e/tests/Feature/Commands/{TopologyCommands,TopologySnapshotCommands}Test.php`.

Out:
- Product behavior stays unchanged: do not edit `apps/gateway/`, `apps/cli/`, or `packages/php-sdk/`. The harness calls their supported Node provisioning and role-convergence operations but adds no production Route-pool behavior, application-placement policy, fleet migration, or session-store setup.
- The shared snapshot stays the exact registered three-Node profile: keep `TopologyProfile`, `TopologySnapshotGeneration`, snapshot identities, refresh/rebuild/cold-replacement construction, and their manifests at Gateway, app-dev, and one app-prod Node. An extended attempt never copies, removes, promotes, or writes `app-prod-2` into the shared snapshot.
- Do not add Gateway or app-dev Nodes, an arbitrary recipe field, a second extension, or more than one extra Node. Reject every extension value other than `app-prod` before a lease, capacity reservation, network, or VM is created.
- Do not change `bin/e2e-scenarios`, `apps/e2e/tests/Scenario/**`, or the disposable cold-scenario authority. Scenario results remain regression evidence and never substitute for the three required issue proof actions.
- Production deployment, production resources, and production release remain outside this harness issue.

## Implementation order

1. Add the optional typed `app-prod` extension to the proof-plan and recipe values, derive the four physical keys and both address families, make end-state/action validation recipe-aware, and prove the no-extension serialization and fingerprint are unchanged.
2. Make the persisted feature-topology and proof-input schemas record the selected recipe, pinned generation, intended instance map, image alias, and observed fingerprint; update state reconstruction and tests before any lifecycle service consumes the new schema.
3. Extract the duplicated discovery/proof resource transaction into `IssueTopologyConstructor`: validate the plan and image first, reserve the recipe count, create the private network, copy the three pinned snapshots, construct `app-prod-2`, and roll back the full intended inventory on any failure. Keep candidate convergence on the standard recipe.
4. Integrate the constructor into acquire and prove. For extended discovery only, run full extension-aware convergence after mounting the worktree; keep the standard discovery path unchanged. Record construction failure before lease removal only when exact rollback succeeds.
5. Generalize convergence, WireGuard provisioning, and verification from singleton app-prod role lookup to ordered physical Nodes. Provision both app-prod Nodes, preserve `e2e-dev` creation and hydration on `app-dev`, require both app-prod Nodes to contain no AppInstances, and add service and network probes for `app-prod-2`.
6. Make fixture staging, proof actions/results, exec/shell diagnosis, immutable guards, and release use the persisted physical inventory. Verify retryable exact cleanup and conflict refusal across all four VMs, mounts, and the network.
7. Bind the topology construction inputs into the immutable manifest and equivalence evaluation, retain complete action evidence, and make promotion refuse every extended plan before mutation. Update developer and closeout guidance for early declaration and refresh-only closeout with release after successful refresh.
8. Write `.loop/proof/ORB-132.json` with `extension: app-prod` and the three Incus actions `extended-topology-ready`, `extended-node-targeting`, and `extended-runtime-connectivity`. Add the flat, self-checking `.loop/proof/extended-runtime-connectivity.sh` fixture. The `extended-runtime-connectivity` action runs on `gateway` with `argv` exactly `['bash', '/var/lib/orbit-e2e/proof/extended-runtime-connectivity.sh', 'app-dev', 'app-prod', 'app-prod-2', '10.44.0.4']`. The fixture reads the post-convergence `nodes`, `instances`, `workspaces`, `app_instances`, `routes`, and `route_targets` tables from the Gateway SQLite database and fails unless the sole AppInstance is `e2e-dev` on physical Node `app-dev` with `node_id` 2, both legacy tables are empty, neither app-prod Node contains an AppInstance, and every Route has exactly one target with no target, Node scope, generation basis, or equivalent graph edge on either app-prod Node. It then fails unless `ping` reaches `10.44.0.4` and a batch SSH command on that address runs a PHP expression, reports PHP-FPM and Caddy active, and validates `/etc/caddy/Caddyfile`. Add a table-driven successful case and one refusal case for each graph and runtime condition to `ProofFixtureContractTest.php`; keep shell pipelines and remote-command failures fail-closed under `ProofFixtureShellContractTest.php`.
9. Run the named focused tests, `cd apps/e2e && composer check`, `composer docs-lint`, and `bin/test`; then prove the exact clean commit with `bin/e2e-topology prove ORB-132` while extended discovery remains the default command target.

## Must preserve

- ADR 0005: the persistent profile and coordinated snapshots remain `gateway`, `app-dev`, and `app-prod`; snapshot state is an acceleration cache whose exact manifests and objects fail closed; normal refresh starts from the promoted generation; promotion and recovery remain deterministic; Incus development never changes production release authority.
- ADR 0006: discovery and proof keep separate attempt IDs, networks, instances, devices, inventories, and state; discovery remains the default command target; proof starts fresh, synchronizes one exact candidate, requires every action to exit zero, and turns post-construction failures into diagnosis; proved topology stays immutable; cleanup revalidates exact ownership and never selects by prefix, age, or broad query; production resources remain separate.
- ADR 0015: proof reuse depends on recorded-input equivalence, not SHA or ancestry alone; the immutable manifest and compact result fingerprints remain mutually checked; the plan and all active fixtures remain proof-contract inputs; unknown or changed runtime/construction inputs fail closed; equivalence stays explainable; review, merge, promotion, and lineage remain bound to exact proved, accepted, included-main, and merged identities; Pest remains required for the combined candidate.
- ADR 0019: physical Node keys remain separate from assigned roles; deterministic names, MACs, addresses, capacity, and exact cleanup use the selected recipe; the scenario lanes, cold constructor authority, and scenario evidence stay independent and cannot become issue acceptance or promotion authority.
- ADR 0035: mutating-proof closeout runs snapshot refresh only after the external merge and current `origin/main` are verified; records proved attempt, accepted head, merge commit, and promoted generation; releases discovery and proof only after refresh promotion; never substitutes refresh for missing, failed, or non-equivalent proof; never edits refresh lineage.
- ADR 0036: the harness provisions supported samples only through AppInstance and Route contracts, keeps the supported `e2e-dev` AppInstance on `app-dev`, creates no AppInstance on either app-prod Node, creates no legacy Instance or Workspace, and adds no migration facility or compatibility path.
- ADR 0037: the shared snapshot remains one fresh three-Node generation; normal discovery and proof clone it; issue extension is not a cold snapshot replacement; the existing generation remains protected until an authorized refresh or promotion completes; ordinary scenarios gain no acceptance or promotion authority.
- ADR 0040: only discovery and proof may declare exactly one additional app-prod Node before construction; they clone the standard three Nodes and construct the extra Node inside the same isolated attempt; extension, construction inputs, and complete inventory are bound to evidence; candidate identity, convergence, acceptance, diagnosis, immutability, ownership, capacity, recovery, and cleanup cover the extra Node; extended proof is non-promotable; closeout refresh preserves the three-Node snapshot and releases both full attempts only after success; the extra Node is never removed to manufacture promotable evidence; scenario evidence is never substituted.
- Existing adjacent invariants: standard plan normalization/fingerprints and three-VM acquisition remain unchanged; the topology snapshot serializers accept only their fixed inventory; checkout source and the `e2e-dev` AppInstance stay on app-dev; both app-prod Nodes remain free of AppInstances; shared-role singleton lookup remains fail-closed unless code explicitly iterates physical Nodes; commands reject unrecorded keys; proved attempts reject mutation; ownership conflicts keep the lease and unrelated Incus resources; every cleanup verifies absence.
