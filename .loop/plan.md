# Feature plan

Issue: ORB-125
Review verdict: BLOCK

## Outcome

Give Apps and AppInstances stable source terms and a reserved `default` identity while keeping each branch-named default source and Route available until an operator completes its manual migration.

## Must preserve

- ADR 0025: one App owns `default_branch`; `default` is the reserved AppInstance identity for the default development source; only that identity receives the unprefixed development hostname; every other name remains the hostname prefix; its identity, placement, and Route stay stable across branch changes; non-default creation falls back to `default_branch`; migration keeps the earlier default Route identity and never overwrites an occupied `default` name or placement.
- ADR 0025 update boundary: a future `default_branch` change must reconcile an existing default checkout or worktree before the setting becomes authoritative and must refuse a source that cannot switch coherently. ORB-125 renames the setting but does not add or weaken that update workflow.
- ADR 0027 creation and ownership: `instance:new` owns a new checkout; an active AppInstance owns one source directory whose layout is `checkout` or `worktree`; a checkout owns its independent repository; a worktree owns only its working directory and linked-worktree administration entry, never the common repository or local branch.
- ADR 0027 lifecycle boundary: `instance:register` owns adoption, movement, repair, inference, and resumable activation; `instance:remove` remains the one removal lifecycle; no unregister surface appears; forced removal never bypasses path, ownership, repository-identity, symlink, or unregistered-worktree safety; worktree removal retains its local branch and no removal deletes a remote branch.
- The App migration preserves nullable incomplete source defaults, one-time remote-default resolution, explicit branch verification, exact idempotent create identity, `app.identity_conflict`, `app.default_branch_unavailable`, repository redaction, strict top-level JSON, and null readback without inference.
- AppInstance creation preserves `reserved -> checkout_prepared -> source_resolved -> active`, locked idempotent retries, immutable Node/root/path ownership, exact repository/branch/starting-commit evidence, managed-path overlap checks, source recovery, and Route creation only after activation.
- A schema upgrade never performs SSH, Git, filesystem, runtime, or Route projection work and never renames or moves a legacy source. SQLite constraints, foreign keys, unique App/name and Node/path ownership, Route targets, and rollback safety remain explicit and fail closed.
- Read access, binary serving-Node authorization, request IDs, bounded errors, recursive redaction, sanitized activity properties, and stable list order remain unchanged. A migration-required report never exposes a checkout path through Doctor issues or error diagnostics.
- Route provenance, target, generation-basis, scope, publication, and pending lifecycle rules remain unchanged. Explicit hostnames stay unchanged; new generated Routes still use Node-first effective TLD selection and independent Node-or-active-Cluster scope; an active Cluster still requires one Router.
- Legacy Instance and Workspace persistence, APIs, source paths, hostnames, Doctor behavior, and staged conversion remain separate and unchanged.
- Doctor remains verify-only with the existing eight families. AppInstance and Route models remain typed inputs to the `instance` family exactly once; the term migration adds no family, mutation, raw diagnostics, or persisted Doctor state.
- The SDK stays framework-neutral typed Saloon transport with the same 68 operations, TLS behavior, omission rules, standard envelopes, response bounds, request IDs, and credential redaction. It contains no Gateway source or migration policy.
- The CLI stays stateless and HTTP-only with deterministic human and JSON output and request-ID errors. It performs no SSH, Git, filesystem, runtime, Route, adoption, or migration work.
- Product implementation leaves dependency manifests, `apps/e2e`, `bin/e2e-*`, unrelated proof plans, GitHub, Linear, production release, and unrelated components unchanged.

## Review findings

- `BLOCK — ISSUE_CREATION_DEFECT` — Acceptance item 4 requires each `default` or named AppInstance to expose one Route-owned hostname through the AppInstance API, SDK, and CLI output, but neither the issue nor ADR 0025 defines which Route supplies that scalar value after the AppInstance is targeted by more than one Route, after target replacement or clearing, or after Route removal. Current `route_targets` persistence permits one AppInstance to be referenced by several Routes, `AppInstance::routeTargets()` is plural, and `CreateRouteAction::ensureForAppInstance()` selects an unordered first matching Route. The plan invents an “activation Route hostname” without a durable activation-Route identity, deterministic selection rule, nullable behavior, or multi-Route proof. The smallest safe resolution is to return ORB-125 to Backlog and amend Acceptance item 4 to choose an observable contract: persist and preserve one primary activation Route relationship, define a deterministic projection and its lifecycle, return a Route collection, or keep hostname output on Route operations only. This is a product/API decision for the repository owner; the plan reviewer cannot choose it.
- `BLOCK — ISSUE_CREATION_DEFECT` — Acceptance item 7 requires a “bounded migration conflict” for an occupied `default` identity or destination, but it does not name the public error code or distinguish the existing-row, managed-path-overlap, and unmanaged-filesystem collision cases. The plan repeats the phrase and leaves the developer to choose or conflate `instance.placement_conflict`, `instance.path_taken`, or a new migration code. Because the exact structured error is observable Gateway, SDK, CLI, and activity behavior, the issue must define the closed code and the collision cases before implementation. The smallest safe resolution is to add the exact code and no-mutation outcomes to Acceptance item 7 and its proof. This is a product/API decision for the repository owner.
- Both blockers were present when ORB-125 was published directly into claimable `Todo` at 2026-09-05T07:39:04Z and moved to `In Progress` at 2026-09-05T07:41:16Z. ADRs 0025 and 0027 were already accepted at the branch base, and the only later current-`origin/main` change is unrelated merge-workflow guidance. Linear has no later comment or relation that supplies either missing contract. The classification is therefore `ISSUE_CREATION_DEFECT`, not `POST_CREATION_DRIFT` or `PREFLIGHT_BLOCKER`.
- `FIX` — Acceptance item 2 and ADR 0027’s consequence for persisted `registered_worktree` state are not covered. The migration boundary converts `managed_clone` but never says whether a pre-existing `registered_worktree` row makes the schema migration fail closed. Mapping it silently to `worktree` would assert Orbit ownership without the explicit operator reconciliation ADR 0027 requires; retaining it would violate the criterion’s exact `checkout`/`worktree` values. State the fail-closed behavior derivable from ADR 0027, add it to `AppInstanceIdentityMigrationTest.php`, and keep that row and source unchanged for the separate `instance:register` owner.
- `FIX` — Acceptance item 5’s Incus proof is not concrete enough to prove an upgrade. The proof runner stages fixtures and converges the candidate, including migrations, before setup and acceptance actions run. Naming only `legacy-default-remains-serving` does not establish a pre-migration branch-named AppInstance and serving Route, run the exact schema upgrade, or verify the same hostname and source response before and after it. Define the issue-local fixture and ordered setup/acceptance argv that create the legacy schema state, perform the candidate migration without moving source, and test the retained Route over the topology. Keep every declared action zero-exit as the repository proof rule requires.
- `FIX` — Acceptance item 8’s documentation audit is incomplete. `docs/domains/applications.md` lines 44, 56, and 99 describe `instance:register` adoption and migration as available behavior even though the first `Out` bullet excludes that API, SDK, CLI, and workflow and the current command surface contains no such command. `docs/reference/apps.md` lines 40–44 tells readers to use an App update operation even though the third `Out` bullet excludes that endpoint and the preserved SDK contract has only four App operations. Revise these pages to state only ORB-125’s manual-migration and update boundaries, without presenting excluded workflows as shipped behavior; report any behavior that needs its separate issue owner.
- `FIX` — Acceptance items 3 and 8 disagree with the App definition in `docs/concepts.md` line 8. A named AppInstance with a matching remote branch does not inherit `default_branch`; it uses that branch and uses `default_branch` only as fallback. Correct the definition so it remains self-sufficient without claiming every AppInstance inherits the setting.
- `FIX` — The changed `docs/architecture.md` duplicates the placement and branch-selection mechanism owned by `docs/domains/applications.md`, contrary to `writing-documentation`’s rule that a core page links to the page owning each detail and never repeats it. Route the source-selection details from the core page to the domain page. Also normalize the retained hard-wrapped paragraph at `docs/reference/apps.md` lines 40–44 so every changed page follows the one-line-paragraph rule. `composer docs-build` and `composer docs-lint` currently exit `0`, but those automated checks do not close these semantic and writing findings.
