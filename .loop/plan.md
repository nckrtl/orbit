# Feature plan

Plan format: 1
Issue: ORB-131
Flow: discovery
Review verdict: PASS

## Outcome

Operators can manage systemd and Docker processes owned only by development or production AppInstances, and AppInstance removal cleans those processes up safely and resumably.

## Code boundaries

In:
- `apps/gateway/app/Models/Process.php`, `apps/gateway/app/Models/AppInstance.php`, `apps/gateway/app/Domain/Processes/`, `apps/gateway/app/Data/Processes/`, `apps/gateway/app/Actions/Processes/`, `apps/gateway/app/Http/Requests/Processes/`, `apps/gateway/app/Http/Controllers/Api/ProcessesController.php`, `apps/gateway/app/Http/Authorization/ServingNodeResolver.php`, `apps/gateway/app/Infrastructure/Activity/CommandActivityTargetResolver.php`, and the process routes and bindings: map the public `instance` token to AppInstance ownership, reject legacy owners before mutation, derive development and production placement on every operation, retain typed validation and AppInstance-owned responses without adding a Node response field, and attribute activities to the AppInstance and target Node.
- New `apps/gateway/app/Domain/Processes/ProcessAdmissionLock.php`, `apps/gateway/app/Infrastructure/Processes/NativeProcessAdmissionLock.php`, its `apps/gateway/app/Providers/AppServiceProvider.php` binding, `apps/gateway/app/Actions/Processes/AddProcessAction.php`, and `apps/gateway/app/Actions/AppInstances/RemoveAppInstanceAction.php`: serialize Process admission and AppInstance removal acceptance through per-AppInstance cross-process owners acquired in stable ID order. Add holds one owner through final locked owner-state validation, Process-row admission, runtime convergence, and final status; removal holds every fixed-set owner while its acceptance transaction revalidates the deletion set and marks all members `removing`, then releases after commit.
- `apps/gateway/app/Infrastructure/Processes/`, `apps/gateway/app/Actions/Doctor/ProcessDoctorProbe.php`, `apps/gateway/app/Infrastructure/Doctor/NativeProcessStateInspector.php`, and the AppInstance removal projector seam: preserve systemd and Docker lifecycle behavior while adding AppInstance execution context, production release checks, bounded Doctor inspection, and exact-owned resumable Process cleanup inside the accepted removal set.
- `packages/php-sdk/src/Requests/Processes/`, `packages/php-sdk/src/Responses/Processes/`, `apps/cli/app/Commands/Processes/`, and their focused tests: make the typed transport and CLI expose only the AppInstance selector and keep AppInstance ownership in Process responses without adding a public Node field, while preserving every runtime option, bounded result, request ID, and redaction rule.
- `apps/gateway/tests/Feature/Api/ProcessesTest.php`, new `apps/gateway/tests/Feature/Domain/ProcessTargetResolverTest.php`, `AppInstanceProcessAdmissionConcurrencyTest.php`, and `AppInstanceProcessCascadeTest.php`, existing Process action, Doctor, authorization, activity, runtime-manager and renderer suites, `packages/php-sdk/tests/Unit/Requests/Processes/ProcessRequestsTest.php`, and `apps/cli/tests/Feature/Processes/ProcessCommandsTest.php`: cover ownership, serialized admission, context, lifecycle, release selection, cascade isolation and retry, and removal of the Workspace surface.

Out:
- Legacy Process records and runtime artifacts remain unconverted and unadopted; do not add a data migration, compatibility selector, or cleanup migration, and do not change legacy `Instance`, `Workspace`, Node-owned Process behavior, fleet preparation, runtime backends, or Schedule implementation.
- Process records never move between AppInstances or Nodes; leave AppInstance source relocation, production deployment orchestration, App process-definition cloning, Route policy, and automatic reconciliation unchanged.
- Harness code remains unchanged; leave `apps/e2e/` and `bin/e2e-*` unchanged and use only existing discovery acquisition, shell, exec, sync, verify, and release commands.

## Implementation order

1. After Tom receives an independent `PASS` for this plan, acquire ORB-131 discovery and record the initial topology and AppInstance placements without changing the E2E harness.
2. Remap the public `instance` Process target to `AppInstance`, add its model relation, remove the Workspace enum and CLI option, narrow SDK constructors to an AppInstance ID, and update HTTP authorization and activity attribution while leaving legacy records and artifacts untouched and unreachable by supported Process operations.
3. Add `ProcessAdmissionLock` with native per-AppInstance cross-process owners and stable ascending multi-owner acquisition. Make `AddProcessAction` acquire the owner after initial resolution and hold it through a transaction that locks and revalidates the AppInstance, admits or resumes the Process row, and commits, then through runtime convergence and final status. Make `RemoveAppInstanceAction` acquire every fixed-set owner after source preflight and before its acceptance transaction, revalidate that exact set while held, atomically mark every member `removing`, and release after commit. Add the controlled concurrency test now so the two valid orderings—add completes and is included before acceptance, or removal accepts and the later add is refused—guard all later cascade work.
4. Refactor `ProcessTargetResolver` into operation-specific AppInstance context resolution for active mutation, start, inspection, and cleanup; derive development checkout, managed user, Route certificate scope, and environment path or production Node, dedicated user, home, `current`, and persistent environment path from recorded placement.
5. Adapt Process specification assembly, systemd and Docker renderers, and `RemoteProcessRuntimeManager` to the new context; preserve all explicit options, stopped installation, exact ownership, atomic replacement, rollback, locks, bounded logs, and redaction, and add start-time release availability checks without restarting a running Process on pointer changes.
6. Update Process API, SDK, CLI, node-access, activity, and Doctor tests and behavior so Process responses retain the AppInstance owner without a new Node field, activity records identify that AppInstance and target Node, Workspace targets fail before mutation, and Doctor inspects unavailable or removal-incomplete state through a bounded read-only path.
7. Add a narrow Process cascade coordinator to AppInstance `runtime_cleanup`: enumerate each member's Process records in stable order, resume failed or removing records, remove only exact-owned artifacts, delete each record after cleanup, run existing AppInstance runtime cleanup afterward, and leave the existing member checkpoint incomplete on any failure so identical removal retries only unfinished work.
8. Add the remaining focused cascade, target-context, API, SDK, CLI, renderer, runtime, activity, Doctor, authorization, and regression tests; run all acceptance-map tests and the three changed-project `composer check` commands.
9. Run and retain the eight discovery observations, restore or reacquire registered discovery state as needed, then run topology sync and verify. Record actual commands, results, resource state, deviations, and the statement `Discovery development only; isolated acceptance proof not run` for implementation handoff.

## Must preserve

- ADR 0036: AppInstance remains the only supported runnable Process owner; Process APIs, SDK operations, CLI selectors, runtime behavior, and compatibility fallbacks do not support legacy Instance or Workspace targets; Orbit supplies no legacy migration tooling, and the fleet operator owns transition and data handling outside Orbit.
- ADR 0038: authorized AppInstance removal includes every owned running, stopped, failed, or removing Process; source-removal preflight precedes child cleanup; shared per-AppInstance serialization makes Process admission complete before acceptance or refuse after acceptance for every fixed-set member; cleanup stops and removes exact-owned artifacts; success leaves no owned Process intent or persistent artifacts; failure remains resumable; other AppInstances, Node-owned state, and unrecognized artifacts stay untouched. Schedule implementation and its existing decisions remain outside this issue.
- ADR 0048: an AppInstance-owned Process is an independent record whose placement and identity come from its AppInstance; an App definition change does not reconcile an existing copy or runtime state, modifying or removing a copy does not change the definition, and the operating agent changes an instance copy explicitly.
- ADR 0046: production Process context stays within the AppInstance's recorded home and dedicated user, persistent `.env` stays outside replaceable releases, `current` selects active code, deployment remains explicit, and Orbit does not infer application commands, automatic rollback, data replacement, or deployment retry from Process lifecycle operations.
- ADR 0047: candidate source and running state remain unchanged, a prepared target Process stays stopped until an explicit start, development-only definitions do not become production state, target application cleanup remains operator-owned, and cloning stays separate from deployment and Process execution.
- ADR 0044: the Gateway derives environment-file location and execution identity from recorded AppInstance placement; synchronization retains its atomic, validated, redacted boundary and never restarts a Process or refreshes application caches.
- ADR 0004: Doctor remains synchronous, bounded, deterministic, read-only, and non-persistent except for its standard activity row; Process observation exposes no commands, paths, raw output, configuration, environment values, credentials, or exception text, and unreachable or failed inspection remains `unverifiable` rather than a mutation request.
- ADR 0011 where not superseded by ADR 0046: production placement uses the dedicated application user and home, AppInstance runtime owns application execution, and role co-location or certificate mode does not let a caller select a different Node or user.
- Existing Process validation, stable error envelopes, request correlation, binary Node access, fixed typed argv, operation deadlines and locks, exact systemd and Docker ownership labels, rollback and recovery artifacts, secret redaction, and non-streaming 1-to-1,000-line log bounds remain intact. Process responses keep their AppInstance owner contract and do not gain a Node field; only activity attribution adds the target Node.
- Existing AppInstance source preflight, Route cleanup, fixed-set ordering, development source deletion, production home retention, dedicated PHP cleanup, final row transaction, and removal progress contract remain intact around the added Process cleanup.
- Product feature work does not change the E2E harness; discovery uses registered topology commands only.
