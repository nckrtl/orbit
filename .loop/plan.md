# Feature plan

Issue: ORB-124
Review verdict: FIX

## Outcome

Make AppInstance removal validate its complete source set before mutation, update or delete its Route safely, and resume a fixed normal or forced deletion from durable progress.

## Code boundaries

Each member stores immutable AppInstance, App, Node, Route, environment, source-layout, canonical repository, path, branch, common-repository, worktree, and ordering evidence plus checkpoints for source preparation, Route target change or deletion, source finalization, runtime cleanup, and row deletion. ## Must preserve

- ADR 0008 removal safety: use immutable recorded source paths and historical roots; validate protected paths, directory boundaries, containment, ownership, canonical paths, symlink-free parents, repository identity, and overlap; delete only exact owned source and an allowed empty grouping directory; never recursively delete a root, ancestor, unexpected sibling, or unrecognized content.
- ADR 0009 ownership and routing: AppInstance remains App plus Node with immutable placement, branch, starting commit, source layout, path, root, and lifecycle evidence; source removal remains refusal-first; force cannot waive structural identity; explicit placement, runtime ownership, DNS-last publication, and legacy conversion stay unchanged. Its general zero-target Route retention rule remains outside removal, while ADR 0041 supersedes that rule when removal clears a final target.
- ADR 0023 hostname and scope: the Route remains the only hostname owner; explicit and generated naming rules, Node-first TLD selection, active-Cluster scope, active Router requirement, workload and Router projections, private/public trust boundaries, and complete-mutation refusal remain unchanged. Removal changes only the target and its derived serving projection after acceptance; it does not rename or rescope the Route.
- ADR 0024 generated target identity: atomic target replacement, generated-hostname derivation, and the retained generation-basis guards remain unchanged for Routes not deleted by AppInstance removal; generated Routes remain single-target. ADR 0041 supersedes targetless hostname, scope, and generation-basis retention when removal clears the final target, so the removal operation releases that hostname only by deleting the Route.
- ADR 0025 stable default identity: `default`, its placement meaning, and its generated Route identity stay stable. A migration-required legacy default is refused before removal and is never treated as an ordinary checkout merely because its path or branch looks compatible.
- ADR 0026 repository ownership: compare supported SSH and HTTPS origins through the one canonical App repository identity; never select the first of ambiguous Apps, change an access URL, merge Apps, or expose credentials or raw Git diagnostics.
- ADR 0027 source ownership: creation owns new checkouts and registration alone owns adoption; an AppInstance owns exactly one `checkout` or `worktree`; a checkout owns its repository directory; a worktree owns only its directory and administration entry. Forced removal may discard dirty or unpublished source and cascade through every registered linked worktree, but never bypass path, ownership, repository, symlink, or unregistered-worktree safety. Retain worktree local branches and every remote branch.
- ADR 0028 sole Route: at most one Route targets an AppInstance and an active AppInstance has exactly one. Establishing `removing` before target clear is the same-operation removal exception; independent target replacement, clear, and Route removal still cannot strand an active AppInstance. ADR 0041 supersedes retained empty-Route behavior for final-target removal.
- ADR 0030 provisioning semantics: active state continues to mean Orbit provisioning and Route configuration, not application health. Removal does not add health gates, infer setup work, or change the behavior of missing dependencies, application errors, or configured setup-step ownership.
- ADR 0041 final-target removal: validate the complete removal set before mutation; remove only the departing target and retain a shared Route while targets remain; delete a final-target Route before source finalization; never retain that empty Route; release its hostname immediately; and keep failures `removing` so retry finishes cleanup without recreating the Route.
- Current-main adjacency: ADR 0038 keeps source preflight before future Process and Schedule cleanup and requires a resumable child-cascade boundary, but ORB-124 does not create Process or Schedule ownership. ADR 0039's exact round-robin pool order, consecutive-failure cooldown, no passive-success revival, request-start availability snapshot, and in-flight completion behavior remain intact when removal converges an existing shared production pool; ORB-124 does not create or rebalance that pool. ADR 0031 keeps production application content after removing a production AppInstance.
- Preserve the locked `reserved -> checkout_prepared -> source_resolved -> active` creation machine, starting-commit evidence, branch override, migration refusal, exact source-layout migration, one canonical repository per App, and current destination and managed-overlap checks. A `removing` row cannot return to a creation state.
- Preserve Route provenance, publication, lifecycle, failure metadata, uniqueness, binary Node access, strict top-level JSON, request IDs, recursive redaction, sanitized activity, and all Node, Cluster, Router, DNS, TLS, Caddy, firewall, and Laravel URL behavior outside the removal-owned target-clear and runtime-cleanup path.
- Preserve SQLite control-plane state and foreign-key/trigger behavior. Removal evidence must survive member row deletion without creating an orphan that can authorize deletion for a different AppInstance, path, repository, or operation.
- The SDK remains framework-neutral typed Saloon transport with 68 operations, bounded DTOs, exact omission, standard envelopes, TLS verification, request correlation, redaction, and no raw response escape hatch. The CLI remains stateless and HTTP-only with deterministic output and request-ID errors.
- Preserve legacy Instance and Workspace source, removal, process, Doctor, hostname, and certificate behavior. Leave Process and Schedule models, runtime managers, and target rules unchanged. Leave dependencies, the E2E harness, unrelated proof state, GitHub, Linear, and production release untouched.

## Review findings

- ORB-124 Acceptance limits the exact no-store `503` wire contract to coordinated normal or forced **development** removal. The Route boundary, acceptance row, implementation step, and committed `docs/reference/appinstance-removal.md` and `docs/reference/routes.md` instead apply that exact response to every final-target Route, including production. That invents a public production response which the current contract does not require. Constrain the exact renderer and proof to development removal. Keep the general final-target requirement from Acceptance and ADR 0041: delete the Route, release its hostname, and do so before source finalization. If the same exact response is intended for production, amend the issue contract first.
- The Scope bullet excluding balancing-policy and multi-target-pool creation changes is crossed by `Must preserve`, which treats “consecutive-failure cooldown, no passive-success revival, request-start availability snapshot” as current behavior. ADR 0039 requires equal-priority round-robin, bounded transport-failure exclusion, no automatic replay, and immediate removal from new request selection, but it does not define those extra semantics. ORB-84 is still Todo, and `origin/main` has no shipped production-pool implementation to preserve. Remove the invented downstream invariants and bound ORB-124 to the ADR 0039 bullets its removal path touches without implementing or documenting balancing policy.
- The shared-production-Route Acceptance row lacks the persistence boundary needed for its proof. On current `origin/main`, `apps/gateway/database/migrations/2026_09_05_000000_provision_development_app_instances.php` rejects an active Route unless it has exactly one target, so the proposed two-app-prod-node fixture cannot represent a valid active Route. Add the forward-migration/trigger boundary and database proof that permit an already-existing explicit production Route to have its ordered target set while preserving generated and app-dev single-target rules and the exactly-one-Route invariant for every active AppInstance. Keep public target-set creation and balancing behavior Out.
