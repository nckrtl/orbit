# Feature plan

Issue: ORB-105
Review verdict: PASS

## Outcome

Adopt a verified caller-local Git checkout or worktree into managed AppInstance ownership, placement, provisioning, and removal through one resumable `instance:register` operation.

Out:

- Do not add an unregister endpoint, SDK request, CLI command, state, or cleanup path. `instance:remove` remains the only AppInstance removal lifecycle, and this issue does not change `apps/gateway/app/Actions/AppInstances/RemoveAppInstanceAction.php` or its removal contracts.
- Do not add or change App source-setting update operations. Registration may call idempotent App creation, but it never changes the repository access URL, canonical identity, `default_branch`, root, or defaults of an existing App.
- Do not delete, rename, push, or otherwise mutate a remote branch. Worktree adoption and removal retain local branches and never make an AppInstance own the common repository of a linked worktree.
- Do not add a generic worktree-creation command or make `instance:new` use worktrees or caller-local source. Its managed independent-clone lifecycle and branch-selection contract remain separate.
- Do not introduce new Route naming, scope, publication, reconciliation, health, or public Ingress policy. Registration reuses the existing singleton development Route and provisioning path; public Ingress stays out of scope.
- Do not change `apps/e2e` or `bin/e2e-*`. The future issue-local proof plan and flat fixtures under `.loop/proof/` use the existing harness.

## Incus observations

- Set `observed_inputs: true` because the registration scenarios execute the app-dev CLI, the Gateway HTTP application, and Gateway CLI setup or inspection on the required `app-dev:cli`, `gateway:fpm`, and `gateway:cli` surfaces during both setup and acceptance.
- Set `mutates: true`. Registration, relocation, provisioning, migration, and removal change reusable Node state even though each fixture traps cleanup, removes its Orbit-owned AppInstances with the established removal command, and restores fixture-owned source and configuration.
- Put the eight issue-named actions in `.loop/proof/ORB-105.json`: `register-checkout-and-worktree`, `register-preserves-git-state`, `registered-source-provisioning`, `registered-source-provisioning-rollback`, `manual-default-migration`, `checkout-move-repairs-worktrees`, `include-worktrees-all-or-none`, and `cross-filesystem-registration-retry`.
- Use flat executable PHP or shell fixtures beside the plan. Each fixture creates only issue-owned repositories, linked worktrees, mount-backed cross-filesystem destinations, and sentinels; records complete before/after manifests; injects one bounded failure at each durable step; and cleans up through public behavior plus fixture-owned restoration. Do not change the E2E harness.

## Must preserve

- ADR 0009 where later ADRs leave it in force: an App owns its AppInstances and Routes; an AppInstance belongs to one App and one Node, owns its recorded path, effective root, branch and starting commit evidence, and lifecycle; runtime prerequisites belong to the Node app role; source safety remains canonical, contained, overlap-free, and refusal-first; Route traffic retains the trusted direct or Router path, route-scoped certificates, Host and TLS server name, LAN-before-WireGuard selection, firewall ownership, and deterministic unavailable response.
- ADR 0016: `app:new` remains idempotent creation rather than update; registration never changes an existing App's identity or source defaults; existing AppInstance paths remain recorded rather than recomputed except for the explicit ADR 0025/0027 migration; repository updates never arise as registration side effects; durable publication keeps pre-publication rollback and post-publication forward recovery distinct; Laravel configuration work preserves unrelated bytes and never logs contents.
- ADR 0017 where ADR 0023 leaves it in force: Cluster membership remains optional; an AppInstance stores one Node and no independently selected Cluster; placement always requires an active compatible app role; membership does not grant or remove roles; standalone Nodes remain supported; source ownership and placement never change merely because Cluster state changes.
- ADR 0023: the Route alone owns the hostname; explicit hostname wins; generated development naming uses Node TLD first and active Cluster TLD only as fallback; app-dev placement requires an effective TLD; active Cluster membership chooses scope independently; Cluster scope requires one active Router and projects through Router and workload Caddy without direct public workload exposure; invalid hostname, scope, target, or role refuses before authoritative mutation.
- ADR 0024: a generated Route derives its hostname and stored generation basis from its target Node; target, basis, hostname, and scope change atomically; the Route retains identity when untargeted; registration creates no multi-target generated Route and never removes a retained basis Node.
- ADR 0025: `default_branch` remains the App source setting; `default` is the reserved default AppInstance identity and only unprefixed generated hostname; other names remain hostname prefixes; default placement and Route identity survive branch-setting changes; registration supplies the explicit guarded migration without overwriting an occupied default identity; non-default fallback still uses `default_branch` only after explicit and matching-name selection.
- ADR 0026: one App owns one canonical repository identity and one supported access URL; equivalent supported SSH and HTTPS forms resolve the same identity; duplicate ownership refuses; checkout lookup returns at most one App; registration never merges, deletes, updates, or chooses between conflicting Apps.
- ADR 0027: `instance:new` creates source and `instance:register` adopts caller-local source; active AppInstances own `checkout` or `worktree`; a worktree never owns its common repository or local branch; adoption moves to managed placement, repairs retained worktrees, preflights a requested complete set, infers only unambiguous facts, requests unresolved interactive values, retains a valid created App, and resumes with one recoverable authoritative path; `instance:remove` remains the sole removal path and never deletes remote branches.
- ADR 0028: one AppInstance has at most one Route and every active AppInstance has exactly one; registration establishes the association before active state; an incomplete registration may retain an unrouted non-active AppInstance; independent Route mutations cannot strand an active AppInstance.
- ADR 0029: Orbit derives a Laravel AppInstance's canonical URL from its sole Route, applies and verifies it before activation, refuses or restores an inconsistent change, and preserves every unrelated application setting.
- ADR 0030: provisioning completes automatically after source, Route, and detected Laravel URL alignment; no separate activation or healthy application response is required; source, runtime, network, TLS, and firewall checks remain; missing dependencies, keys, databases, or application errors do not make the provisioned records inactive; registration infers no setup step or dependency install.
- Existing `instance:new` tests keep independent-clone source preparation, explicit branch selection, `reserved -> checkout_prepared -> source_resolved -> active`, exact starting evidence, idempotent provisioning, singleton Route creation, and additive output unchanged.
- Existing removal tests keep normal and forced preflight, checkout/worktree ownership, fixed-set cascade, remote-branch retention, source-operation locks, final-target Route deletion, production target retention, checkpoints, quarantine receipts, and safe retry unchanged. Registration adds owned source that the landed removal lifecycle already understands; it does not alter removal behavior.
- Existing API boundaries keep active-peer authentication, binary Node access, strict top-level JSON, numeric resource binding, stable ordering, request correlation, bounded errors, recursive redaction, and sanitized activity. Caller locality never becomes a caller-supplied Node ID.
- The SDK remains framework-neutral typed Saloon transport with TLS verification, exact omission and explicit-value semantics, bounded DTOs, standard errors, correlation, and no raw-response or Gateway-policy escape hatch.
- The CLI remains stateless and HTTP-only except for bounded read-only discovery of the current local Git source. It performs no SSH, sudo, remote policy, source relocation, Git mutation, runtime work, or cleanup and retains deterministic output and request-ID errors.
- Dependency manifests, unrelated components, App updates, generic worktree creation, public Ingress, the E2E harness, GitHub, Linear, rewritten Git history, and production release remain unchanged. Future `.loop/proof/ORB-105.json` and flat fixtures are issue-specific evidence inputs, not harness changes.
