# Feature plan

Issue: ORB-72
Review verdict: BLOCK

## Outcome

Add a Gateway-owned Schedule runtime that derives Node or AppInstance execution context, converges one protected systemd projection with recoverable lifecycle state, records generation-bound completion, and reports bounded verify-only Doctor findings.

## Code boundaries

In:

- `apps/gateway/database/migrations/*create_schedules_table.php`, `apps/gateway/app/Models/{Schedule,Node,AppInstance}.php`, and `apps/gateway/app/Domain/Schedules/{ScheduleTargetType,ScheduleCompletionStatus,ScheduleSpecification,ScheduleOperationException}.php`: persist a UUID lookup identity, exactly one restrictive Node-or-AppInstance target, target-local lowercase-name uniqueness, bounded calendar, command, and timeout intent, shared provisioning/active/failed/removing lifecycle state, installed Node, opaque installation generation, bounded latest-completion generation/classification/time, and nullable bounded failure metadata. Use separate nullable target foreign keys with an XOR constraint, target-specific unique indexes, and migration-level guards against direct target Node or execution-identity changes. Keep command and calendar values out of generic serialization and debug output. A matching target/name/specification retry reuses one resumable row; a different specification conflicts without changing it.
- `apps/gateway/app/Domain/Schedules/{ScheduleTarget,ScheduleTargetResolver,ScheduleTargetGuard}.php`, `apps/gateway/app/Actions/Schedules/AddScheduleAction.php`, and `apps/gateway/tests/Feature/Domain/{ScheduleTargetResolverTest,ScheduleLifecycleTest}.php`: accept only the target reference and bounded Schedule specification, then derive the installed Node, runtime user, and working directory from authoritative placement. A Node target uses its managed user and home; an app-dev AppInstance uses its recorded checkout and managed runtime identity; an app-prod AppInstance uses the App's dedicated production user and operator-owned home. Require active compatible Node, placement, role, and runtime state. Do not accept an installed Node, user, home, or working-directory override.
- `apps/gateway/app/Domain/Schedules/{ScheduleRenderer,ScheduleProjection,ScheduleProjectionManager,ScheduleProjectionLock}.php`, `apps/gateway/app/Infrastructure/Schedules/**`, `apps/gateway/app/Providers/AppServiceProvider.php`, `apps/gateway/tests/Unit/Domain/Schedules/ScheduleRendererTest.php`, and focused tests under `apps/gateway/tests/Feature/Infrastructure/Schedules/**`: derive the protected script path and service/timer names only from the UUID; render the command only as protected script input; render root-owned units with fixed `ExecStart`, derived `User` and `WorkingDirectory`, the stored timeout, validated calendar, and `Persistent=true`; and execute only closed SSH, `sudo`, `systemctl`, `journalctl`, `systemd-analyze`, and lock argument vectors. Hold the Schedule database lock and one Node-local operating-system lock, render and verify all candidates before mutation, reject unowned names, snapshot exact owned artifacts and timer state, install and verify the complete projection, and restore or remove only attempt-owned state on failure. Map every remote, timeout, verification, conflict, and rollback failure to bounded Schedule errors without sensitive values or raw results.
- `apps/gateway/app/Actions/Schedules/{AddScheduleAction,RunScheduleAction,ShowScheduleLogsAction,CompleteScheduleAction,RemoveScheduleAction}.php`, the Schedule lifecycle types and projection seams above, and `apps/gateway/tests/Feature/Domain/ScheduleLifecycleTest.php`: converge an add or identical retry, start the same oneshot service non-blockingly, return logs under fixed line/byte/time bounds, accept completion only from the installed Node for the current not-yet-completed generation, and remove safely. Removal claims `removing`, disables and stops only the timer, lets an active service finish, removes only recognized owned artifacts after it stops, and retains retryable state after any failure. Completion stores no command, output, or run history and ignores stale, duplicate, foreign-Node, and post-replacement callbacks.
- `apps/gateway/app/Http/Controllers/Api/ScheduleCompletionsController.php`, `apps/gateway/app/Http/Requests/Schedules/CompleteScheduleRequest.php`, and the narrow completion entry in `apps/gateway/routes/api.php`: expose only the fixed node-authenticated generation-completion callback required by the protected wrapper. Resolve the active WireGuard peer as the callback Node, accept only UUID, generation, and bounded completion classification, call `CompleteScheduleAction`, and create no Activity. Do not add an operator-facing Schedule route or any list, add, show, run, logs, or remove HTTP surface.
- `apps/gateway/app/Domain/Schedules/ScheduleTargetGuard.php`, `apps/gateway/app/Actions/AppInstances/RemoveAppInstanceAction.php`, `apps/gateway/app/Actions/Nodes/{ProvisionNodeAction,RemoveNodeAction,RemoveNodeRoleAction}.php`, and `apps/gateway/tests/Feature/Domain/ScheduleLifecycleTest.php`: refuse target deletion, installed-Node removal, app-role removal, Node managed-user changes, AppInstance Node changes, and AppInstance execution-identity changes while a Schedule exists. Run the guard before state claims, force/offline behavior, or remote mutation. Keep restrictive foreign keys and migration-level update guards as the final direct-write safety boundary for target deletion, Node user changes, App slug changes that derive an app-prod user, and AppInstance placement or working-directory identity changes.
- `apps/gateway/app/Domain/Doctor/{DoctorFamily,ScheduleDoctorIssueCode,ScheduleInspectionData,ScheduleStateInspector}.php`, `apps/gateway/app/Actions/Doctor/{RunDoctorAction,ScheduleDoctorProbe}.php`, `apps/gateway/app/Infrastructure/Doctor/NativeScheduleStateInspector.php`, `apps/gateway/app/Providers/AppServiceProvider.php`, `apps/gateway/tests/Unit/Architecture/DoctorModelCoverageTest.php`, `apps/gateway/tests/Feature/Domain/ScheduleDoctorProbeTest.php`, and focused infrastructure binding/inspector tests: add Schedule as the one checked model in the explicit `schedule` family between `workspace` and `tool`; extend enum dispatch and filtering by token without a numeric family-count assertion; query Schedules by installed Node in stable order; and inspect only the exact UUID namespace through bounded read-only commands. Report stable codes for required-artifact, owner/mode, specification, timer-state, calendar, context, callback, placement, orphan, unreachable, and inspection failures. Reduce expected and observed values to bounded booleans, enums, identifiers, fingerprints, and fixed sentinels.

Out:

- Keep Workspace targets, central dispatch timing, queues, jobs, workers, run-history tables, generic execution frameworks, replay, catch-up, failover, and high-availability timer replicas out of the Gateway. Existing Workspace and Process models, actions, and runtime projections stay unchanged.
- Do not add Schedule edit, rename, enable, disable, replacement, automatic movement, reinstallation, migration, or rebalancing actions. The only state replacement path is explicit remove followed by add.
- Keep the public operator API, PHP SDK, and CLI unchanged. Do not add Schedule operator controllers or requests beyond the node-only completion callback, public Schedule routes, authorization/activity subjects, SDK requests or responses, CLI commands, or surface-count changes; ORB-73, ORB-3, and ORB-71 own those surfaces.
- Do not install the Orbit CLI on workload Nodes, deploy application content, change production release behavior, or change `apps/e2e/**` or `bin/e2e-*`. Runtime proof uses `.loop/proof/ORB-72.json` and issue-local fixtures through the existing harness contract; this planning task does not edit them.

## Must preserve

- ADR 0013, stored intent and installed projection ownership: preserve UUID-only public and artifact identity, bounded target-local names, exactly one Node or AppInstance target, separate target and installed-Node relationships, native calendar/command/timeout intent, lifecycle, opaque generation, bounded latest completion, complete-specification retry identity, and the absence of Workspace, central scheduler, queue, worker, run history, or generic execution state.
- ADR 0013, derived execution context: derive Node target user/home, app-dev runtime user/recorded checkout, and app-prod dedicated user/production home from authoritative active placement and required roles. Never accept installed Node, user, home, working directory, or effective web root as Schedule caller input. Refuse deletion, Node removal, placement changes, and execution-identity changes while intent exists instead of moving it automatically.
- ADR 0013, protected artifacts: keep exactly one root-owned protected script, one root-owned oneshot service, and one root-owned persistent timer per installed generation, all named only from UUID. Keep command text only in non-writable script content; keep fixed `ExecStart`, derived service context, stored timeout, one systemd overlap boundary, the same non-blocking manual-run path, and the fixed generation-completion wrapper.
- ADR 0013, recoverable convergence: validate bounded intent and target context before mutation; validate calendars and candidates on the installed Node through fixed argv; hold both database and Node-local locks; snapshot only exact recognized ownership; reject unknown names; verify the installed projection before activation; restore exact prior artifacts and timer state on failure; retain explicit non-active retry evidence after rollback failure; and never select paths, units, users, or commands from caller-controlled infrastructure arguments.
- ADR 0013, small lifecycle: retain only list, add, show, run, logs, complete, and remove as the architectural operation set, while this issue implements only the runtime and node callback needed beneath the later public surface. Keep run/logs/completion/removal semantics generation-safe and bounded. Keep edit, rename, enable, disable, generic command, numeric public lookup, persisted logs, and arbitrary output absent.
- ADR 0013, sensitive values and completion authority: accept completion only from the recorded installed Node and current generation with no Activity. Keep command, calendar, logs, paths, users, unit contents, credentials, and raw remote results out of errors, Doctor, Activity, debug metadata, and generic model output. Keep logs bounded and never claim arbitrary application output can be redacted reliably.
- ADR 0013, Schedule Doctor: add Schedule as an explicit checked model in the `schedule` family between transitional `workspace` and `tool`; use family tokens rather than transitional or final counts; inspect only with bounded read-only commands; report the complete stable drift set; restrict orphan discovery to the exact Schedule namespace; and expose only bounded booleans, enums, identifiers, fingerprints, and fixed sentinels.
- ADR 0013, proof and release: prove real systemd, SSH, identities, permissions, timers, services, journald, timeout, callback, rollback, completion, and removal on one disposable Ubuntu 26.04 Incus topology. Never treat that proof topology as production or alter production deployment and release behavior.
- ADR 0004, verify-only boundary: Doctor may read the Gateway and registered Nodes but never converges, installs, reloads, enables, starts, stops, adopts, repairs, completes, removes, locks with external side effects, or persists findings. Schedule inspection stays separate from the mutating projection manager.
- ADR 0004, explicit deterministic families and model partition: preserve enum and dispatch ownership, canonical requested-filter ordering, stable Node/resource/issue ordering, one checked-family disposition per direct model, typed prerequisites separate from checked resources, and no registry or generic comparison pipeline. ADR 0013 alone extends the transitional eight-family order with `schedule` after `workspace`.
- ADR 0004, shared Node observation and bounded reports: preserve one base Node observation per selected Node, unreachable and inspection-failed reduction, healthy empty families, checked-resource counts, status precedence, stable issue shape, typed code catalogs, safe unknown-code fallback, and the ban on raw diagnostics and sensitive expected/observed values.
- Existing AppInstance source and Route behavior remains unchanged: Schedule resolution reads placement but does not mutate App, AppInstance, checkout, Route, Cluster, Caddy, PHP-FPM, source, branch, commit, root, hostname, scope, or traffic state. Existing target and removal tests stay green except for the required Schedule guards.
- Existing Process projections retain their model, target forms, names, units, commands, lifecycle, logs, and Doctor family. Schedule artifacts use a distinct UUID namespace and do not adopt, overwrite, inspect, or remove Process or role-owned systemd state.
- Existing Node provisioning, role removal, force/offline removal, SSH host-key pinning, WireGuard peer identity, command deadline, protected input, recursive redaction, and bounded exception behavior stays intact. Schedule guards run before these paths mutate anything and do not weaken their current recovery rules.
- Dependency manifests, public Schedule operator routes, authorization/activity subjects, PHP SDK, CLI, workload-node CLI installation, production deployment, and the E2E harness remain unchanged. The proof plan and its issue-local fixtures use only the existing harness contract.

## Review findings

- BLOCK — `PREFLIGHT_BLOCKER`: ORB-72 is currently blocked by ORB-81, and ORB-81 is still `Todo`. Acceptance item 2 requires app-prod AppInstance placement, runtime user, and working-directory resolution, but current `origin/main` has only app-dev AppInstance creation and its `app_instances` table has no recorded app-prod user or home. ORB-81 owns those immutable stored values and explicitly requires an App slug change to leave them unchanged. This plan instead derives the app-prod user from the App and proposes a Schedule guard on App slug changes. The smallest safe resolution is to complete and merge ORB-81, rebase ORB-72 onto that exact `origin/main`, and rewrite the target resolver, mutation guards, documentation, and focused proof against ORB-81's delivered stored identity. This is the existing Linear dependency boundary and requires no new ORB-72 product decision.
- BLOCK — `ISSUE_CREATION_DEFECT`: ORB-72 Scope requires validation of names, commands, calendars, users, paths, timeouts, and target context, ADR 0013 requires bounded Schedule input, logs, completion classifications, errors, and stable Doctor codes, and Acceptance items 4 and 12 require those bounds to be observable. The issue, plan, and `docs/reference/schedules.md` say only `bounded` or list drift categories. They do not fix the Schedule name grammar and length, calendar and command byte limits, timeout unit and range, log line/byte/time limits, completion tokens, or exact `schedule.*` Doctor issue-code catalog and category granularity. An implementer and later API/SDK consumers would have to invent public behavior, while the reference page does not supply the inputs, failure codes, or limits required by `writing-documentation`. ADR 0013 was accepted on `origin/main` before ORB-72's most recent transition to `Todo` on 2026-09-04, and no later ADR or code change introduced this gap. The smallest safe resolution is for the issue owner to add the exact bounded values and stable code catalog to ORB-72, then align the plan, reference page, and focused domain, logs, completion, and Doctor catalog proofs. These values are a Linear product-contract boundary.
- FIX — ORB-72's public API exclusion assigns Schedule requests, controllers, and routes to ORB-73, whose current contract includes the generation-completion operation. The plan nevertheless adds `ScheduleCompletionsController.php`, `CompleteScheduleRequest.php`, and an API route in ORB-72. That crosses the Scope exclusion and also omits the existing `RecordCommandActivity` boundary that would otherwise create an Activity for the callback. Remove the HTTP controller, request, and route from this plan and keep only the generation-bound completion action and fixed wrapper callback contract below the later ORB-73 transport surface.
- FIX — Acceptance items 10 through 12 and ADR 0004's explicit dispatch, typed code catalog, canonical order, and bounded unknown-code fallback touch existing Doctor boundaries that the plan omits. `DoctorIssueCodeCatalog.php` has an exhaustive family match, `DoctorReportContractTest.php` hard-codes the family order and exact code catalogs, `DoctorTest.php` hard-codes the API family order, and `RunDoctorActionTest.php` owns dispatch and filter-order proof. `DoctorModelCoverageTest.php` cannot prove those behaviors. Add these files to the code boundaries and add focused cases for the `schedule` token, canonical position, dispatch, exact stable catalog, unknown-code fallback, and unchanged ordering and report behavior.
- FIX — The `docs` label and `writing-documentation` rule prohibit a maintained page from restating ADR Decision bullets. `docs/reference/schedules.md` repeats ADR 0013's intent fields, derived execution context, three-artifact projection, convergence and rollback sequence, lifecycle and removal behavior, Doctor boundary, and exclusions almost section for section. `composer docs-lint` passes, but it does not enforce this semantic ownership rule. Keep the self-contained concept definition, replace ADR-owned architecture and rationale with links, and retain only one operator-facing reference contract with the exact inputs, outputs, failure codes, limits, and observable results supplied by the corrected issue.
