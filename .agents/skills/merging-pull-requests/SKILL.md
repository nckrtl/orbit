# Closing Out Pull Requests

Close out one independently approved pull request after the external orchestrator merges it. This task does not review, approve, or merge.

## Delivery flow

Run `bin/loop-flow status` in the issue worktree and read [Implementation loop](../../../docs/reference/implementation-loop.md). Name the selected `discovery` or `proof` flow in every handoff. The separately published `.loop/flow.json` binds the choice to the candidate; a missing selection defaults to `discovery`. Proof is opt-in: select `proof` explicitly before planning or reviewing. A repository-default change does not change an existing worktree.

## Closeout

1. **Verify the candidate.** Require one independent `Approved.` review bound to the exact head and published artifact SHA and flow, a passing Builder-run root `composer check` receipt for it, no actionable findings, and no later commit. Run `bin/loop-artifacts fetch <ISSUE> --candidate=<approved-head> --expected-artifact=<artifact-sha>`. Successful validation establishes the parent, file-boundary, file-type, and expected-SHA checks; do not repeat them manually. Validate again when either SHA changes and investigate failures before continuing. For an older worktree, use the current main helper from that worktree as described in [artifact references](../../../docs/reference/implementation-loop.md#artifact-references). Artifact validation does not establish approval, acceptance, selected-flow evidence, or merge authority. In `proof`, require current main included in that head. A changed head needs fresh approval, a fresh Builder gate, and an evidence decision under its selected flow. Main movement alone does not invalidate a discovery candidate. Never create an artifact removal commit.
2. **Verify the external merge.** Require authoritative read-only GitHub state to report that this head merged into main. Fetch `origin/main`. Run `bin/loop-flow verify-merge --candidate=<approved-head> --merge=<merge-sha>` in the issue worktree. Require the approved head as its exact second parent. In `proof`, require the same tree; in `discovery`, require the conflict-free Git merge tree of the recorded parents, which can include newer main changes. Missing or mismatched lineage is a stop.
3. **Verify acceptance evidence.** In `discovery`, require the reviewed acceptance assessment, focused checks, a passing Builder gate, and development observations when `incus` is required; skip proof inspection. Automated-only issues without `incus` need no topology evidence in either flow. In `proof` with `incus`, inspect the captured result, topology identity, input manifest, exact plan and fixtures, every declared action's zero exit, and the separate completed review record. Require exact or equivalent evidence for the approved head and included main. When the report selects candidate convergence, require its successful result bound to that head and report. Require the captured successful proof topology to remain active; replacement or explicit abandonment is the only pre-closeout release path. Never substitute snapshot refresh for missing acceptance proof.
4. **Advance primary main; close out retained proof only in proof flow.** Locate the primary checkout with `git worktree list --porcelain`. If its clean main is an ancestor of fetched `origin/main`, advance it with `git -C <primary> merge --ff-only origin/main`. With detached HEAD equal to origin/main, update local main with `git -C <primary> branch -f main origin/main`. Read HEAD, main, and origin/main back. Before stopping on any other primary mismatch, queue `bin/tia-cache refresh --background --repository=<primary>` from a checkout with the current helper; its owned main checkout does not depend on primary cleanliness. In `discovery`, skip every snapshot operation and record the accepted head, artifact SHA, flow, and merge. In `proof` for Incus issues, run `bin/e2e-topology closeout <ISSUE> --candidate=<approved-head> --artifact=<artifact-sha> --merge=<merge-sha> --main-sha=<current origin/main>`. Require that main contains the verified merge. Closeout refreshes the shared snapshot from that merged main and releases the exact retained proof topology only after refresh succeeds. A failed refresh retains the topology, captured evidence, and review record for retry; it does not undo the merge. Record proved attempt, artifact SHA, accepted head, merge commit, and resulting generation in the closeout handoff. Follow any extra issue-specific harness proof contract.
5. **Queue cache maintenance and clean resources.** `bin/worktree-remove` queues `bin/tia-cache refresh --background` after verifying the branch merged. When cleanup will not call that command, queue refresh explicitly from a checkout that has the current helper, using `--repository=<primary>`. Queue it even when unrelated primary edits prevent advancement; refresh owns a separate clean main checkout. Record the durable request and log path; do not wait for completion or make cache availability a cleanup or next-feature gate. A failed correctness check on main goes to the monorepo maintenance owner and holds unrelated merges until verified recovery. Do not copy a feature cache into main. See [main test baselines](../../../docs/reference/implementation-loop.md#main-test-baselines). In `discovery`, release any retained discovery and run `bin/worktree-remove <ISSUE>`; no proof capture or snapshot refresh is a closeout gate. Preserve published artifacts. The remaining steps apply to `proof`: require idle discovery to have been released before review and the successful proof lease to be absent after closeout. Release any candidate-convergence attempt with `--candidate`, then run `bin/worktree-remove <ISSUE>`. The removal command releases a retained diagnosis but refuses to release or remove an active successful proof; verified closeout owns that exact release. For Incus issues, verify the snapshot identity. Verify absence of issue resources and local feature branch, and absence of `.loop/` from main in either case. Keep artifact refs and the primary checkout's evidence archive. Return documentation findings for separate handling.

Run mutations as bounded commands and verify their resulting state. GitHub evidence is read-only. Approval, selected-flow evidence, merge lineage, and cleanup remain required in both flows. Current-main integration, complete acceptance proof, and snapshot convergence apply only to `proof`. Before the next feature, require primary main clean and run `bin/worktree-create`: it fetches origin, fast-forwards main, queues background cache maintenance, and bootstraps from compatible successful publications. Preserve unrelated primary edits in their owning task; never reset or stash an active writer's work. GitHub CI is not a gate. See ADRs 0049, 0050, 0051, 0052, 0053, 0054, and 0059.
