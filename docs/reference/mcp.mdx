# MCP server

The Gateway serves a Model Context Protocol (MCP) server so an agent can operate Orbit without the CLI. Every Gateway API operation is one tool. The tool runs the same request the matching CLI command sends, so validation, node access, redaction, and command activity behave the same on both paths.

## Endpoints

Both endpoints speak MCP over streamable HTTP with `POST`, and both offer the same catalogue.

| Endpoint | Tools it lists | Use it when |
| --- | --- | --- |
| `https://gateway.orbit/mcp` | One tool for every API operation. | The client loads tool definitions on demand, or the context has room for the full catalogue. |
| `https://gateway.orbit/mcp/search` | `search_tools` and `execute_tools`. | The client loads every listed tool into its context. The agent searches the catalogue, then runs up to 25 calls in one request. |

`search_tools` returns exact tool names with their complete input schemas; an empty query browses the catalogue. `execute_tools` takes `{"calls": [{"name": "...", "arguments": {...}}]}`, runs the calls in order, and stops at the first error.

## Identity and access

The caller is the Node whose WireGuard address the connection comes from, the same identity the API uses. There is no token and no login.

- A connection from an address that is not an active Node receives HTTP `403` with `peer.identity_unknown` before it can list tools.
- Each tool call repeats that check and applies directed node access ([`node:access:add`](/cli/node#orbit-nodeaccessadd)) inside the API request it runs. A Node without an access edge to the serving Node receives the API's `403` as the tool error.
- The Gateway certificate chains to the Orbit root certificate authority (CA). A Node that Orbit manages already trusts it. On another machine, run `orbit gateway:trust` first.

## Tools

A tool's name is the operation's identifier in the [API reference](/api/overview), `<family>-<verb>`: `node-list`, `instance-show`, `process-restart`, `route-create`. Its input is one object that holds the operation's path parameters, query parameters, and JSON body fields together; the server places each value where the operation expects it. A `DELETE` path parameter such as `route` on `route-destroy` therefore travels in the tool arguments and on the path. If the same id also appears in the JSON body, the API treats it as path identity. Its annotations mark a `GET` as read-only and a `DELETE` as destructive.

A successful call returns the API's JSON document as text, usually `{"data": ..., "meta": {"request_id": ...}}`. A failed call returns a successful MCP transport response whose tool result has `isError: true`. Its `content` carries the API error envelope with the status added; the HTTP response itself is not the API's error status:

```json
{"isError": true, "content": [{"type": "text", "text": "{\"status\":422,\"error\":{\"code\":\"validation.failed\",\"message\":\"...\",\"details\":{\"slug\":[\"...\"]}}}"}]}
```

For a disabled extension, a direct `tools/call` returns `isError: true` and content containing `status: 409` and `error.code: extension.disabled`; HTTP 409 is reserved for the underlying API request, not the MCP transport. The same tool error is returned by `execute_tools` when a stale call names a tool that was filtered from the catalogue, and execution stops at that call. The server checks the generated tool's extension metadata before catalogue filtering can turn a stale direct call into a generic not-found error.

`instance-deploy` and `instance-rollback` stream progress over HTTP. As tools they run to completion and return every progress event in order under `events`; the last event carries the result.

Four operations are machine callbacks and have no tool: the realtime channel signature, the Grafana access check, the Instance wake page, and the schedule completion report.

The `tasks-*` tools belong to the Gateway-switched [tasks](/reference/tasks) extension, except `tasks-status`, which is a core assistance view that remains available while tasks is off. The `proxycli-*` tools belong to [proxycli](/reference/proxycli). A disabled extension is omitted from both `tools/list` and `/mcp/search`; a direct `tools/call` or stale `execute_tools` call returns an MCP tool error with `isError: true`, content carrying `status: 409` and `error.code: extension.disabled`, and does not execute the API route. `tasks-create` requires Gateway access. `tasks-update` and the `tasks-subtask-*` tools need access to the Node that holds the group's Instance, or to the Gateway for a group without one. `tasks-create`, `tasks-subtask-create`, and `tasks-subtask-update` take each subtask's typed [deliverables](/reference/tasks#deliverables) as a `deliverables` array, and `tasks-show` returns them.

## Connect a client

Claude Code, from a Node or a WireGuard peer that trusts the Orbit CA:

```bash
claude mcp add --transport http orbit https://gateway.orbit/mcp
```

Any client that takes a JSON server entry:

```json
{"mcpServers": {"orbit": {"type": "http", "url": "https://gateway.orbit/mcp/search"}}}
```

A client built on Node.js reads extra CAs from `NODE_EXTRA_CA_CERTS`; point it at the Orbit root CA file when the system store is not used.

## Keep the catalogue current

`apps/gateway/resources/mcp/tools.json` is generated from `docs/openapi.json`. Each generated operation records its extension slug, or `core` when it is always available. The normal MCP server and `OrbitSearchServer` filter that metadata against the Gateway enabled set before building their catalogues. After a change to a route, form request, or data class, regenerate both:

```bash
bin/docs-openapi
bin/mcp-tools
```

`bin/docs-openapi --check` reports a stale API reference, and `bin/mcp-tools --check` and `composer mcp-tools` report a stale manifest. Continuous integration runs both checks. The Gateway test suite fails when an API route has no tool or a tool has no route, so the MCP catalogue cannot trail the API.
