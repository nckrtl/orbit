# Realtime events

The Gateway broadcasts one realtime event for every record it changes, so a client such as the [web app](/reference/web-app) can stay live without polling. This page defines the envelope, the channel and its authorization, the full catalogue of event types, and the node role that configures delivery.

## Transport

The Gateway never runs a broadcast server. It only broadcasts, as a Pusher-protocol client, to an external Laravel Reverb server reachable at `wss://reverb.orbit`. A client that wants realtime updates connects to that Reverb server directly and subscribes to the `orbit` channel; it does not connect to the Gateway for the WebSocket itself.

Every broadcast happens synchronously, inside the same request that changed the record. The Gateway does not use a queue for broadcasting, matching its no-queues rule. A Reverb outage never fails the request that changed the record: the Gateway logs a warning (`Failed to broadcast a record event.`) and continues. A client cannot tell from an API response whether its change was also broadcast; it can only tell whether the change itself succeeded.

## Channel and authorization

Every event broadcasts on one private channel, `orbit`. A client authorizes access the same way it calls the rest of the API: as an active WireGuard peer Node, identified by its source address, against `POST /api/v1/broadcasting/auth`. Any authenticated Gateway API caller may subscribe; there is no per-Node scoping on this channel. An unauthenticated caller, or a caller whose peer address does not match an active Node, receives `403`.

Node agents publish on separate per-Node presence channels, not on `orbit`. See [Node agent channels](#node-agent-channels).

## Discovery

A client asks the Gateway where Reverb is instead of carrying hand-edited connection settings. `GET /api/v1/realtime` requires the same active WireGuard peer identity as the rest of the API and returns:

```json
{
  "data": { "url": "wss://reverb.orbit", "key": "<reverb-app-key>", "channel": "orbit" },
  "meta": { "request_id": "..." }
}
```

`url` and `key` are `null` when broadcasting is not configured, that is when no `websocket` role is active on the fleet:

```json
{
  "data": { "url": null, "key": null, "channel": "orbit" },
  "meta": { "request_id": "..." }
}
```

`channel` is always `"orbit"`, whether or not broadcasting is configured, so a client can read it once and reuse it across both shapes.

## Envelope

Every event shares the same shape. The broadcast name equals `type`.

| Field | Contract |
| --- | --- |
| `type` | `<family>.<verb>`, for example `node.created`. Also the broadcast name a client subscribes to. |
| `id` | The changed record's id. A string annotation ID for annotations; a numeric id for every family except deploy steps, which use the step's name. |
| `at` | ISO 8601 timestamp of the broadcast, in the Gateway's timezone. |
| `data` | For annotation notices, `{ id, instanceId, revision }`. For other changes, the record exactly as its list or show endpoint returns it: the same Spatie Data object, unchanged. A `deleted` event carries a minimal snapshot instead, usually just `id` and a name or slug, because the action deletes the record before the broadcast and leaves nothing else to serialize. |

```json
{
  "type": "process.status",
  "id": 42,
  "at": "2026-09-18T10:15:00+00:00",
  "data": { "id": 42, "name": "web", "status": "active", "runtime_status": "running", "...": "..." }
}
```

## Verbs

Most families broadcast `created`, `updated`, and `deleted`. Three families also broadcast `status`, reserved for a change to the Gateway's own recorded runtime state rather than to configuration: process start, stop, and restart. Node and Instance runtime state changes are not currently broadcast; see [Limits](#limits).

## Event catalogue

### Node

| Type | Fires when | Data |
| --- | --- | --- |
| `node.created` | A Node is provisioned for the first time. | `NodeData` |
| `node.updated` | An existing Node is reprovisioned, its settings change, it is retargeted to a new public SSH host, or a role is added or removed. | `NodeData` |
| `node.deleted` | A Node is removed from the fleet. | `{ id, name }` |

### Project

| Type | Fires when | Data |
| --- | --- | --- |
| `app.created` | A new Project is created. | `AppData` |
| `app.updated` | A Project's slug, repository, default branch, or root changes. | `AppData` |
| `app.deleted` | A Project is removed. | `{ id, name, slug }` |

### Instance (`instance`)

| Type | Fires when | Data |
| --- | --- | --- |
| `instance.created` | An Instance is created or registered for the first time. | `AppInstanceData` |
| `instance.updated` | An Instance's deployment branch changes, or its removal begins but has not yet deleted the record. | `AppInstanceData` |
| `instance.deleted` | An Instance is fully removed. | `{ id, name }` |

### Process

| Type | Fires when | Data |
| --- | --- | --- |
| `process.created` | A new Process is added. | `ProcessData` |
| `process.status` | A Process is started, stopped, or restarted. | `ProcessData` |
| `process.deleted` | A Process is removed. | `{ id, name }` |

### Schedule

| Type | Fires when | Data |
| --- | --- | --- |
| `schedule.created` | A new Schedule is added. | `ScheduleData` |
| `schedule.updated` | A Schedule is activated, records a completed run, or begins removal without finishing it in the same request. | `ScheduleData` |
| `schedule.deleted` | A Schedule is fully removed. | `{ id, name }` |

### Database connection (`database`)

| Type | Fires when | Data |
| --- | --- | --- |
| `database.created` | A new database connection is registered. | `DatabaseConnectionData` |
| `database.updated` | A database connection's fields change. | `DatabaseConnectionData` |
| `database.deleted` | A database connection is removed. | `{ id, slug }` |

### Firewall rule (`firewall`)

| Type | Fires when | Data |
| --- | --- | --- |
| `firewall.created` | A new firewall rule is stored. | `FirewallRuleData` |
| `firewall.deleted` | A firewall rule is removed. | `{ id, name }` |

There is no `firewall.updated`. Storing a rule under a name that already exists requires the same action, source, protocol, and port as the stored rule; any difference is refused as a conflict, so there is no path that changes a stored rule's fields.

### Route

| Type | Fires when | Data |
| --- | --- | --- |
| `route.created` | A new Route is created directly through the routes API. | `RouteData` |
| `route.updated` | A Route's domain or publication changes, or its target is set or cleared. | `RouteData` |
| `route.deleted` | A Route is removed. | `{ id, domain }` |

A Route that Orbit creates implicitly while provisioning an Instance does not emit its own `route.created`; only a Route created directly through the routes API does.

### Deploy step (`deploy_step`)

| Type | Fires when | Data |
| --- | --- | --- |
| `deploy_step.created` | A deploy step is added to an Instance's deployment recipe. | `DeploymentStepData` |
| `deploy_step.updated` | A deploy step's command, phase, timeout, or position changes. | `DeploymentStepData` |
| `deploy_step.deleted` | A deploy step is removed. | `DeploymentStepData` (the removed step's last known fields) |

A deploy step has no numeric id in its API shape, so `id` carries the step's name instead. `data` matches the deploy-step list and show endpoints exactly, so it does not include the owning Instance's id.

## Limits

An event broadcasts only when its triggering action returns successfully. An operation that fails after it already wrote failure evidence onto a record, such as a `failed_step` or `error_code`, does not broadcast that write: the action throws before it reaches the broadcast call, and the HTTP response already reports the failure.

An idempotent create call, such as adding a Process, Schedule, or firewall rule that already exists with identical configuration, returns the existing record without change and does not broadcast. Only a call that creates a genuinely new record broadcasts a `created` event.

`node.status` and `instance.status` are not currently emitted, even though they exist for parity with `process.status`:

- A Node's own recorded status only changes as a side effect of provisioning, removal, or a role change, and each of those is already covered by `node.created`, `node.updated`, or `node.deleted`. No Gateway action flips only a Node's status field.
- Instance dev-runtime hibernation (wake and sleep) tracks "awake" and "asleep" through a marker store outside the Instance and Process rows. It never writes a field either record's list or show endpoint returns, so the Gateway has nothing on the record to broadcast.

`process.status` carries the Process's own persisted lifecycle status and desired state, not the live runtime string its show endpoint also reports (the state a process manager observes right now, such as whether the OS process is currently running). That live string is polled at read time, not recorded anywhere, so a change in it alone cannot be broadcast. The Node agent publishes live runtime state to subscribers of its [Node agent channel](#node-agent-channels) instead.

Repairing a Node's DNS resolver (`orbit node:dns-repair` and similar recovery paths) re-pushes already-stored WireGuard and DNS configuration to the peer. It does not change the Node record, so it does not broadcast.

## Configuration

Broadcasting turns on by assigning the `websocket` node role, which installs and runs Reverb itself; see [Realtime events with Reverb](/solutions/realtime-reverb):

```bash
orbit node:role:add gateway websocket --converge
```

There is no environment variable to set. The Gateway resolves the active connection (host, port, scheme, and the Reverb application credentials it generated for the role) from the role assignment itself, lazily and once per request, and configures its `reverb` broadcast connection from it before every broadcast. The Gateway connects to the role's Node by its WireGuard address while still presenting and verifying the name `reverb.orbit`, because the Gateway host does not resolve names through Orbit's private DNS. The role's Caddy site for `reverb.orbit` joins the Node's WireGuard-address listener when another site binds that address. When the Node's other sites bind only the wildcard address, it binds the wildcard too, so it never takes their traffic. Removing the role removes the connection, the certificate, the Caddy site, the private DNS record, and the stored credentials; `GET /api/v1/realtime` then reports `url` and `key` as `null` again.

### Annotation

`annotation.updated` fires after an annotation transaction commits. Its data is `{ id, instanceId, revision }`, a small invalidation notice rather than the full record. Clients fetch the Instance annotation list to recover current state. Screenshot and comment payloads stay out of broadcasts.

## Node agent channels

Each Node has a presence channel, `presence-node.{id}`, where its [Node agent](/reference/node-agent) publishes presence and Process runtime state. The Gateway does not broadcast on these channels. Its agent view subscriber joins every channel and keeps the latest state as the [Gateway view](/reference/node-agent#gateway-view). [ADR 0129](/decisions/0129-publish-node-presence-and-process-state-on-per-node-presence-channels) records the channel design, and [ADR 0148](/decisions/0148-keep-a-gateway-view-of-node-agent-state) records the Gateway view.

### Membership

| Member ID | Who | Signed by |
| --- | --- | --- |
| `agent.{id}` | The agent of Node `{id}` | `POST /api/v1/agent/broadcasting/auth`, only for a request from Node `{id}`'s own WireGuard address when that Node is managed. |
| `gateway.{socket id}` | The Gateway's agent view subscriber | The subscriber itself, with the Reverb app secret the Gateway holds. No HTTP request is involved. |
| `viewer.{socket id}` | Any other subscriber, such as a browser | `POST /api/v1/broadcasting/auth`, with the same rules as `orbit`. |

A member's `user_info` is `{ "kind": "agent", "node_id": 12, "version": "0.1.0" }` for the agent, `{ "kind": "gateway" }` for the subscriber, and `{ "kind": "viewer", "node_id": 7 }` for a viewer, where a viewer's `node_id` is the Node the viewer connects from. The existing auth endpoint never signs an `agent.*` or `gateway.*` member. It refuses any other `presence-*` channel, including a malformed `presence-node.*` name, with `broadcast.channel_forbidden` (403). Presence events tell a subscriber when the agent joins (`pusher:member_added`) and leaves (`pusher:member_removed`). A clean agent stop and an agent crash both close the connection, so the agent leaves at once.

### Events

The agent publishes Pusher client events. Reverb adds the sender's `user_id` to each one. A subscriber must ignore an event on `presence-node.{id}` unless its `user_id` is `agent.{id}`.

| Event | When | Data |
| --- | --- | --- |
| `client-heartbeat` | Every 5 seconds. | `{ sequence, at }` |
| `client-snapshot` | After the agent joins, when a new member joins, and after the agent reconnects to Docker. | `{ sequence, at, docker, part, parts, units }` |
| `client-process` | As soon as a unit or container changes, after 250 milliseconds of merging. | `{ sequence, at, unit }` |

| Field | Contract |
| --- | --- |
| `sequence` | A counter that increases with every event from one agent run. It restarts at 1 when the agent restarts. |
| `at` | ISO 8601 UTC time at which the agent sent the event. |
| `docker` | `available` or `absent`. |
| `part`, `parts` | This part's number, from 1, and the number of parts. The agent splits a snapshot so that each message stays under Reverb's 10,000-byte limit. The parts arrive in order with consecutive `sequence` values, and a subscriber applies the snapshot once it has every part. |
| `units` | A list of `unit` entries: every `orbit-process-*` unit and container the agent sees. |
| `unit` | `{ name, runtime, runtime_status }`, for example `{ "name": "orbit-process-42-web", "runtime": "docker", "runtime_status": "exited" }`. `name` has no `.service` suffix. `runtime` is `systemd` or `docker`. |

A snapshot replaces what a subscriber knows about the Node's units. A unit missing from a complete snapshot, or from a `client-process` event since, has no unit or container. Its Process reads as `inactive` for systemd or `exited` for Docker.

A subscriber applies a `unit` entry to a Process only when the Process runs on Node `{id}`, uses the same runtime, and `name` equals `orbit-process-{process id}-{process name}`. It ignores every other entry.

### Presence

A subscriber treats the Node's agent as online while `agent.{id}` is a member and a heartbeat, snapshot, or change arrived in the last 15 seconds. It treats the agent as lost when the member leaves or the 15 seconds pass without an event. A subscriber that has not seen the agent since it subscribed knows nothing about the Node from this channel and uses another source, such as Prometheus.
