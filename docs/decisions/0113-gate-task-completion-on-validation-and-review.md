# ADR 0113: Gate task completion on validation and review

Typed task comments record implementation and review outcomes. Jev identifies missing outcomes or requests for assistance from thread evidence. Gateway verifies the required results before advancing work. Tasks that need assistance retain their capacity and record each request and resolution.

## Status

Accepted on 2026-09-22. Implemented in the Gateway task workflow; independent review and merge remain pending.

This amends the routing choices in [ADR 0110](/decisions/0110-route-task-sessions-with-laravel-ai-jev) and the task lifecycle in [ADR 0103](/decisions/0103-absorb-commander-tasks-as-a-gateway-extension).

## Context

Status filtering identifies tasks that need attention while in progress, but a stopped agent has not necessarily completed its assignment. Completion claims need validation evidence and mechanical checks. Automatically answering input or continuing a blocked agent can hide failures. Assistance needs an audit trail so operators can identify recurring failures and compare applied solutions.

Project `composer check` omits the full test suite. Both `composer test` and `composer test:affected` use test impact analysis, which can select a subset or no tests. The completion gate needs a clear command contract that includes the full project suite.

## Decision

Use the AgentThread and driver boundary from [ADR 0112](/decisions/0112-isolate-agent-threads-behind-drivers). Workflow code consumes normalized state and thread messages, including tool output; runtime payload parsing stays inside the driver.

The following requirements replace automatic drain and continue actions when implemented. AgentThread state remains authoritative: check in-progress tasks with attached sessions and skip message inspection and Jev classification while a session is starting or working.

- Agents and the task UI post typed comments through a Gateway API endpoint. The endpoint stores the comment and its task and session context. For implementation and review outcome comments, the tick checks AgentThread state and verifies the required evidence before acting. Assistance-request and resolution comments trigger their actions immediately as specified below.
- Each task supports typed comments with the full body, author, timestamp, and task identity. Reviewer outcome comments also identify the review attempt, reviewer thread, and driver turn. Assistance requests and resume resolutions are typed comments too, preserving the applied solutions alongside the activity trail.
- After successful `composer check`, the implementer posts `ready_for_review` with a reference to the validation evidence for its current completion attempt and driver turn. Once the session stops working, Jev checks the command output in the last five messages before Gateway notifies the reviewer. The typed comment supplies the implementation outcome without requiring Jev to infer it. The comment does not replace command evidence, authorize a commit, or complete the subtask. Record its handled identity to prevent duplicate handoffs.
- If the stopped implementer has no `ready_for_review` comment for its current attempt, Jev examines its messages. When Jev recognizes successful implementation, Gateway reminds the implementer to post the comment and provide any missing validation evidence. This uses the existing allowance of one implementer reminder per completion attempt. Do not notify the reviewer until the comment and valid evidence exist. An unresolved omission requests assistance.
- A reviewer posts either `changes_requested` with the full findings or `approved` with its approval and `commit_sha`. For the final subtask, `approved` also includes `pr_url`. After the reviewer session stops working, Gateway uses the most recent reviewer outcome comment for the current review attempt without asking Jev to infer that outcome. An approval still requires Jev to check the validation output. Ignore outcomes from earlier attempts. Record the handled comment identity to prevent duplicate delivery or transitions.
- For `changes_requested`, Gateway relays the full comment body verbatim to the existing implementer thread, returns the task to implementation, and starts another review cycle after the implementer finishes and validation succeeds. For `approved`, Gateway performs the validation and artifact checks before advancing the task. A comment does not bypass mechanical checks.
- If a stopped reviewer has no outcome comment for its current attempt, Jev examines its messages. When Jev identifies requested changes or approval, remind the reviewer to post the corresponding typed comment. Do not relay inferred feedback or advance the task before that comment exists. This uses the existing allowance of one reviewer reminder per completion attempt; an unresolved omission requests assistance.
- When classification is needed, Jev returns one of three outcomes: `completed_successfully` for successful implementation or review approval, `changes_requested` for actionable reviewer feedback, or `assistance_required` for input requests, failures, ambiguous completion, or low confidence. `changes_requested` applies only to reviewers. Jev checks validation output. Gateway owns feedback delivery, reminders, artifact verification, and task transitions. Working sessions, already-handled turns, and attempts with a matching outcome comment do not need outcome classification, so Jev has no `noop` outcome.
- When an eligible implementer or reviewer has no outcome comment for its current attempt, Jev identifies the missing outcome or the need for assistance. Use the last five thread messages, including their tool output, alongside the assigned brief. A completion claim alone is not proof that checks passed. Input requests, failures, ambiguous completion, and low confidence request assistance. Actionable reviewer findings return to the implementer for correction.
- `composer check` becomes the completion gate for each changed project: guidance checks, formatting, Rector, static analysis, and the full project test suite. `composer test:affected` remains available for development feedback. Require successful completion-gate evidence covering the latest changes before commit and before PR creation. Subsequent code changes invalidate earlier passing evidence.
- The agent runs `composer check` in its AgentThread. Jev inspects the last five messages, including tool output, to confirm that the command ran and passed for the latest changes. This validation check also applies when a typed completion comment exists. Use the actual command output, not an assistant claim that checks passed. No separate validation record or evidence API is required.
- Missing validation evidence permits one automatic reminder per completion attempt to run the required checks and report their results. Do not notify the reviewer until evidence is present. Failed checks or evidence still missing after that reminder request assistance. An agent response to that reminder remains part of the same completion attempt and does not reset the allowance.
- The implementer prepares the changes without committing. Its first implementation pass ends with `composer check`, a `ready_for_review` comment referencing that run, and a completion message, with no intervening code changes. The reviewer records requested changes in a typed comment for Gateway to relay to the implementer. The implementer addresses them in its own AgentThread, runs `composer check` as its final implementation command, then posts `ready_for_review` referencing that run and sends its completion message to request review again. It makes no code changes between that check and the completion message. Jev checks the output in the implementer thread; discussion in the separate reviewer thread does not affect that window of five messages. This loop continues until the reviewer approves or an agent requests assistance.
- The reviewer owns the approved commit. After approval and successful validation, the reviewer creates one commit for the subtask. Record the branch HEAD when each subtask starts. Gateway verifies that the approval references a new commit for that subtask on the expected branch, that it is the current HEAD, and that the working tree has no staged, unstaged, or untracked changes. Only then mark the subtask done and start the next one. After the final subtask, the reviewer creates the PR. Gateway verifies the referenced PR belongs to the expected repository, uses the group branch and expected target branch, and includes the approved commit.
- Gateway recognizes the reviewer's `approved` comment and checks the commit and PR mechanically. If the reviewer approves but omits the expected commit, final PR, or their references, send one automatic reminder per completion attempt to the reviewer. Keep the task in progress until the required artifacts are verified. An unresolved omission after the reminder or another failed mechanical check requests assistance.
- Persist the driver turn identity and the action already handled for each task. Repeated ticks must not send the same review request or reminder again. A response to a reminder does not reset its allowance; missing evidence or artifacts after the response requests assistance. A new completion attempt resets the reminder allowance only when the implementer submits revised work after reviewer feedback or an operator submits a resolution comment to resume the task. Repeated completion claims do not start a new attempt.
- Temporary Agent driver or Jev communication failures are counted per task. Log each failed tick and retry on the next scheduled tick. On the fifth consecutive failed tick for that task, request assistance with the failure reason and retain its concurrency slot. A successful check for that task resets the failure count; skipped ticks do not increment it. One task failing must not prevent checks of other tasks. This retry threshold applies to communication failures, not reported implementation failures or failed validation checks.
- Posting an `assistance_requested` comment immediately flags the task and its parent group as needing assistance, records the reason and state change in the activity log, and sends the assistance notification once. The task remains in progress and retains its concurrency slot. Do not wait for a tick or call Jev for an explicit assistance request. Jev remains the fallback when a stopped agent reports a blocker without posting the comment.
- A task requesting assistance remains in progress and retains its concurrency slot. Store `assistance_requested`, its reason, and its timestamp, and make the flag visible on the task and parent group. Flagged tasks do not repeat escalation notifications or receive new Jev decisions until explicitly resumed.
- Submitting a typed `resolution` comment is the resume action. Require a non-empty body explaining the applied solution or how to proceed. In one transaction, store the comment, clear the assistance flag, write the activity-log entry with the actor, start a new completion attempt, and reset the reminder and communication-failure counters. The task remains in progress and keeps its concurrency slot.
- Immediately after recording the resolution, relay its full content directly to the blocked AgentThread to continue the agent. Do not wait for a scheduled tick or require a separate resume request. Record delivery against the resolution comment and make retries idempotent so the same resolution cannot continue the agent twice. If delivery fails, preserve the resolution in history and keep the task visibly blocked until continuation succeeds.
- Record an assistance request comment, its state change, and its activity-log entry in one transaction. Log assistance requests, resolutions, and delivery failures with the actor and timestamp. Each new assistance cycle preserves earlier requests and applied solutions for analysis of recurring failures; clearing the flag must not erase the trail.
- Each tick checks the expected PR for groups awaiting merge. A merged PR triggers the existing completion and cleanup path. A closed, unmerged PR or failed cleanup requests assistance. Completion and cleanup must tolerate repeated ticks without repeating successful work. The slot remains occupied until the PR is merged and the group is completed.
- Run `tasks:tick` once per minute. Scheduled and manual invocations use the same Gateway lock so only one tick can run at a time. If another tick holds the lock, skip the invocation without routing tasks or claiming pending work.
- After processing current work and merge completion, check capacity before starting a pending task group. Retain the limit of 10 active task groups per node. Reserved, running, reviewing, and settling groups count toward that limit, including groups awaiting assistance or merge. Recalculate capacity after successful group completion. Fill all available slots in the same tick by selecting the oldest pending groups that fit the remaining node capacity. Reserve and count each slot before provisioning or starting agents, then recalculate capacity before selecting another group.

## Rejected alternatives

- Let the implementer commit before approval: the reviewer must create the single approved commit after the implementer addresses review findings.
- Complete work based only on an agent's claim: the claim does not prove validation or review approval.
- Use affected tests as the completion gate: a selected subset or a zero-test result does not establish that the full suite passes.
- Repeat automatic reminders without a limit: this can hide a blocked task and consume resources indefinitely.
- Release capacity on escalation or PR creation: the group is still in progress until its PR is merged and completion succeeds.
- Overwrite assistance history on resume: this removes the evidence needed to compare solutions when the task blocks again.

## Consequences

- Agents have one completion command, and full-suite runs increase validation time.
- Existing task routing, typed comments, activity logging, resolution delivery, completion checks, and concurrency handling need implementation changes.
- Thread inspection must include command output within the last five messages so Jev can verify `composer check` results.
