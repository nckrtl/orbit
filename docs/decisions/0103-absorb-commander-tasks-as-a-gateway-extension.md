# ADR 0103: Absorb Commander tasks as a Gateway extension

Commander feature work moves into Orbit as the enable-gated Gateway extension `tasks`. A TaskGroup is one parent feature with an ordered list of Task subtasks. The Gateway owns persistence, concurrency, the MCP create, list, show, and complete surface, shared App instance provisioning, T3 spawn on the instance-owning Node, pull-request open, the opt-in Coder settle webhook, and instance removal after merge.

## Status

Proposed. Amended on 2026-09-21 for T3-capable placement and fail-closed spawns. The original record let a refused `project.create`, `thread.create`, or opening `thread.turn.start` leave the group `running` without thread ids. That is withdrawn below.

[ADR 0112](/decisions/0112-isolate-agent-threads-behind-drivers) proposes an `AgentThread` and `AgentDriver` boundary to replace this record's direct T3 integration. ADR 0112 defines the current driver boundary.

## Context

Commander owns feature decomposition, implementer and reviewer threads, and pull request handoff outside Orbit. Orbit already owns Apps, App instances, Routes, node access, and the MCP catalogue generated from the Gateway API ([ADR 0086](/decisions/0086-offer-the-api-as-mcp-tools)). Absorbing Commander work without a new forever-on core surface would either bury an experimental scheduler in every Gateway or force a second control plane to keep polling Nodes.

What matters is an enable-gated boundary, one App instance shared by a feature's subtasks, binary Gateway access for create, and concurrency that the Gateway can enforce without node-side polling.

This record does not reopen the product choices locked on 2026-09-20: the `tasks` extension, polymorphic `taskable` with App instance as the only v1 target, TaskGroup plus ordered Task, one fresh App instance per group, agents on the T3 server of the instance-owning Node, per-subtask implementer plus one long-lived reviewer thread, default models, post-PR Coder notify, and a Gateway-owned Node ceiling of ten active groups. There is no per-Project ceiling.

Slice 1 persisted records and enforced enablement and ceilings. Slice 2 provisioned the shared workspace and started T3 threads. This slice opens the pull request after the last reviewer sign-off, fills settle metrics, posts the opt-in Coder webhook, and removes the instance when an authorized caller completes the group.

## Decision

- `tasks` is a Gateway extension, not a core forever-on family. Enable and disable persist on the Gateway settings scope. Create, add, list, show, and complete refuse with `tasks.disabled` while the extension is off. Enable, disable, and status stay available so an operator can turn the surface on.
- A TaskGroup is the parent feature. It stores a brief (deliverables and acceptance), status, optional reviewer thread id, optional pull-request URL (`pr_url`), a notify-Coder flag (`notify_coder`, Commander's `notify_on_settle`), default implementer and reviewer model names, and settle metrics (tokens, line diff, duration). Ordered Task rows are the subtasks. Each Task stores its own brief, status, optional implementer thread id, position, and settle metrics.
- `taskable_type` and `taskable_id` are a Laravel morph on the TaskGroup. v1 accepts only `App\Models\AppInstance`. A new decision is required before another morph target is stored. A group may exist with a null taskable until InstanceProvisioning assigns the shared App instance.
- One fresh App instance belongs to the group. Subtasks reuse it. `TaskWorkspaceProvisioner` implements InstanceProvisioning. It places the instance on an active Linux Node that has an active `app-dev` role, a WireGuard address, an active `t3-code` Process whose desired state is `running`, and room under the Node ceiling. The recorded Process state is the placement signal, not an HTTP health probe. The instance name and `branch_override` are `task-{group id}`. When `origin/task-{group id}` is missing, source resolution creates that branch from the Project `default_branch` and checks it out. Orbit monorepo groups (`app.slug === 'orbit'`) use a non-visitable instance: an isolated checkout on that feature branch with no Route. That instance stays `source_resolved` because an active AppInstance still requires exactly one Route. Real apps stay visitable: the usual development provisioner creates the inspect subdomain and activates the instance. When no eligible Node exists, or source defaults are incomplete, the provisioner returns null and the group stays `reserved`.
- Agents run on the T3 server of the Node that owns that App instance. `T3AgentSpawner` implements AgentSpawner. It talks to that Node over WireGuard with stock T3 HTTP: `POST /api/orchestration/dispatch`. The body is a flat command (`type` at the top level, not nested) and always includes `headers: []`. A successful dispatch needs a sequence. `threadId` is optional: `project.create` returns `{sequence}` only, and the dispatcher keeps a caller thread id when T3 omits one. ModelSelection `options` are `{id, value}` objects (`id: effort` with `high` for the reviewer and `low` for the implementer). A bare map such as `{effort: high}` is rejected by T3. When `project.create` refuses because that workspace root already has an active project, T3's invariant is `Active project '{uuid}' already exists for workspace root '{path}'`. HTTP dispatch wraps that as `EnvironmentInternalError` / `orchestration_dispatch_failed` and omits the phrase from the JSON body. The Gateway parses the project id from that phrase when it appears in the error body, a nested cause, or a header, and otherwise adopts the active project for that workspace root from `GET /api/orchestration/snapshot`. After a successful `thread.create`, a refused `thread.turn.start` is retried once, logged at error, and leaves the thread id unset. Each subtask gets a fresh implementer. The group keeps one long-lived reviewer thread that receives "please review" handoffs. The reviewer creates a git commit in the shared checkout as the sign-off receipt before the next subtask. Default models are Codex Luna Lite (low) for the implementer and Claude Opus (high) for the reviewer. Per-App configuration is a follow-up decision.
- The scheduler keeps at most one Task `running` in a group so each subtask can commit on its own. Opening starts only the lowest-position pending task and never loops the rest. `acceptReview` starts the next pending task only after the accepted task is completed and no sibling is `running`. A path that would mark a second task `running` or spawn its implementer fails closed with `TaskSequenceException` and leaves that task pending. Reviewing, pending, and completed stay as designed. The long-lived reviewer thread is unchanged.
- After the last subtask is signed off, the group moves to `settling`. That is the reviewable state: the Gateway opens the GitHub pull request, stores `pr_url`, writes tokens, line diff, and duration, and posts the Coder webhook when `notify_coder` is true. The Gateway opens the PR from the reviewer workspace with `gh pr create` when `gh` can, and otherwise through the GitHub HTTP API when `ORBIT_TASKS_GITHUB_TOKEN` covers the App repository. A refused open leaves `pr_url` empty and keeps the group `settling` so create does not fail closed. Task tokens and per-subtask line diffs come from that thread's T3 HTTP snapshot (`GET /api/orchestration/threads/{threadId}`), which replaces Commander's Codex App Server session observer. Group tokens sum those implementer sessions plus the reviewer thread. Group line diff stays the shared checkout against the Project default branch. Showing an active group refreshes the same fields. A refused T3 snapshot keeps the last stored values.
- The opt-in Coder webhook mirrors Commander's `notify_on_settle`. Create accepts `notify_coder` or `notify_on_settle`. The Gateway POSTs a JSON body to `ORBIT_CODER_WEBHOOK_URL` and signs `timestamp.body` with HMAC-SHA256 using `ORBIT_CODER_WEBHOOK_SECRET`. The headers are `X-Orbit-Timestamp` and `X-Orbit-Signature: sha256=…`. The body carries tokens, line diff, duration, and the pull-request URL. A missing URL or secret, or a refused Coder response, skips notify and does not fail settle.
- `tasks:complete` is the merge and explicit-complete path. An authorized Gateway caller marks a `settling` group `completed` and removes its App instance through the existing App instance remover, including any visitable Routes. A second complete is idempotent. The Gateway App receives no GitHub merge webhook ([ADR 0098](/decisions/0098-read-github-repositories-through-a-gateway-owned-github-app)).
- The Gateway scheduler claims the next queued group that fits the Node ceiling of ten active groups. Active statuses are reserved, running, reviewing, and settling. There is no per-Project ceiling. The Node ceiling applies once the morph points at an App instance. After MCP create, the Gateway claims immediately. Provision and T3 HTTP run after the reserve write so a long checkout or dispatch does not hold the claim lock. There is no node-side poll and no web UI for create.
- MCP tools are the generated API tools for enable, disable, status, create, add, list, show, and complete ([ADR 0086](/decisions/0086-offer-the-api-as-mcp-tools)). Create, add, and complete require Gateway access (`ServingNode::Gateway`): the caller is the active Gateway peer or a Node with a grant to the Gateway. List and show use collection access so any authorized peer can read. The MCP layer adds no extra identity.

### Session viewing

The Gateway persists TaskAgentSession links with group, optional subtask, role, Node, and T3 thread ID. These links outlive Instance removal and preserve earlier attempts. Thread IDs on Task and TaskGroup remain the current scheduler pointers. The web app shows the group's sessions below Subtasks and filters implementers on a subtask page. Titles and prompts include task identifiers; database links are authoritative.

A read-only Gateway relay subscribes to one persisted T3 thread over WebSocket and sends snapshots and events to the browser over SSE. Gateway access is required for transcripts. Clients cannot supply an upstream URL or arbitrary thread ID. T3 credentials stay server-side. Sequence-based resume and periodic connection rotation keep the synchronous PHP boundary bounded. T3 owns transcripts; Orbit does not copy conversation history into its database.

## Rejected alternatives

- Core forever-on task tables: rejected because the scheduler, T3 spawn, and Commander cutover remain unfinished and must be switched off without a Gateway downgrade.
- A dedicated Taskable table or a required App instance foreign key: rejected because a second owner such as a Node-only chore needs the same morph, and a group must be stored before InstanceProvisioning assigns the instance.
- Node-side polling for capacity: rejected because the Gateway already knows App and Node placement and can claim in the create request.
- Web UI create: rejected because agents create through MCP, and a UI would invite a second unauthorized path.
- Queued Laravel jobs for claim: rejected because the Gateway keeps infrastructure work synchronous ([Gateway application boundaries](https://github.com/nckrtl/orbit/blob/main/apps/gateway/.ai/rules/app.md)). Claim runs in the create request and through a focused scheduler class.
- CLI-local extension only, with always-on Gateway routes: rejected because that Herdr pattern would leave task writes available to every authorized peer as soon as the API exists.
- Marking a non-visitable instance `active` without a Route: rejected because SQLite still enforces one Route on every active AppInstance.
- Wrapping T3 dispatch in a nested `command` object: rejected because stock T3 expects a flat dispatch body and an explicit `headers` array.
- Opening pull requests through the Gateway-owned GitHub App: rejected because that App is read-only ([ADR 0098](/decisions/0098-read-github-repositories-through-a-gateway-owned-github-app)). Writes stay with `gh` in the reviewer workspace or a dedicated `ORBIT_TASKS_GITHUB_TOKEN`.
- An inbound GitHub merge webhook for cleanup: rejected because the Gateway App receives no webhooks. Complete is an explicit MCP and API path that reuses App instance removal.

## Consequences

- An operator enables `tasks` on the Gateway, then an agent with Gateway access creates a group through MCP. The Gateway persists the group and claims it when ceilings allow.
- A claimed group leaves `reserved` when the provisioner assigns an instance on a Node that still has capacity and T3 accepts the reviewer and first implementer spawn. A missing remote task branch does not block that assignment: the workspace is created from `default_branch`. Missing Nodes and incomplete App source defaults leave the group `reserved` without an instance. A spawn that returns no thread id, whether `project.create`, `thread.create`, or the opening `thread.turn.start` refused it, marks the group `failed`, marks the subtask `failed` when an implementer spawn is the one that refused, and logs which spawn returned no thread id. That applies to both opening spawns and to the implementer spawn that each remaining subtask receives after a sign-off, so the Gateway no longer leaves a group `running` with a null reviewer or implementer thread id. Create still answers with the created group and its `failed` status rather than raising, so one group's refused spawn cannot break an unrelated create. A workspace-root collision adopts the existing T3 project instead of leaving the group without threads.
- A pending Task stays pending until reviewer sign-off completes the running sibling. TaskScheduler refuses a second running sibling and does not spawn that implementer.
- After the last sign-off the group is `settling` and ready for Coder review. A successful PR open stores `pr_url`. Opt-in Coder notify uses the documented HMAC headers and environment keys.
- `tasks:complete` removes the instance and any visitable Routes after merge. Non-visitable Orbit workspaces have no public URL.
- Commander data migration and retiring the Commander app stay out of this decision.
- Authorization stays binary node access. This decision does not add Laravel policies or granular grants.
