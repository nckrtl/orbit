# Realtime events with Reverb

## Problem

`orbit top` and other realtime CLI views need the Gateway to push events instead of the CLI polling for them. The Gateway broadcasts with Laravel's `reverb` driver over one Reverb app, and the CLI subscribes to one private channel named `orbit`. That needs a WebSocket server (the Pusher protocol) reachable at `wss://reverb.orbit`.

## Cause

Reverb itself must not become another Orbit-specific service baked into the monorepo. It is a plain Laravel app with no knowledge of Apps, App instances, Routes, or the CLI. Orbit installs and runs it itself, as the `websocket` node role, the same way the `metrics` role installs and runs Prometheus and Grafana.

## Solution

### The one command

```bash
orbit node:role:add gateway websocket --converge
```

Today the `websocket` role has to go on the same node as the `gateway` role, because that is the only node reaching `reverb.orbit` needs to be pointed at; the role has no conflict with `gateway` or `vpn`. Nothing else is required: no App, no App instance, no deploy step, no custom proxy Route, and no `.env` edit on the Gateway.

### What converge installs on the node

Role prerequisites install `caddy`, `composer`, `git`, `openssl`, `php-curl`, and `php-xml` first. `php-curl` and `php-xml` provide `ext-curl` and `ext-dom`, so `composer install` succeeds on a fresh Ubuntu 26.04 Node that does not already run the Gateway PHP stack. The same two packages are role prerequisites on `app-dev` and `app-prod` hosts.

Converge then checks out a plain, unmodified Laravel app (`https://github.com/nckrtl/orbit-reverb.git` by default) at `/opt/orbit/websocket`, runs `composer install --no-dev`, and writes that app's own `.env` with a generated `APP_KEY` and the Reverb application credentials the Gateway generated for this role assignment. It installs and enables `orbit-websocket.service`, a systemd unit that runs `php artisan reverb:start --host=127.0.0.1 --port=8790` with `Restart=always`.

Alongside the app itself, converge reserves `reverb.orbit` as a private hostname, issues it an Orbit CA leaf certificate, and renders a Caddy site on the role's node that terminates that certificate and reverse-proxies to the local Reverb process; `reverse_proxy` admits a WebSocket upgrade by default. Gateway private DNS answers `reverb.orbit` with the role's node WireGuard address, the same way it answers `gateway.orbit` and `metrics.orbit`.

The repository, ref, install path, and port all have config defaults (`ORBIT_WEBSOCKET_REPOSITORY`, `ORBIT_WEBSOCKET_REF`, `ORBIT_WEBSOCKET_INSTALL_PATH`, `ORBIT_WEBSOCKET_PORT`) and rarely need to change.

### Moving the role to another node

Add the role to the new node, then remove it from the old one:

```bash
orbit node:role:add <new-node> websocket --converge
orbit node:role:remove <old-node> websocket --converge
```

Adding the role converges the checkout, the systemd unit, the certificate, the Caddy site, and repoints the `reverb.orbit` DNS record to the new node in the same step. The Gateway keeps the one generated set of Reverb credentials across the move, so no client reconfiguration is needed.

## Limits

This covers one Reverb instance behind one `websocket` role assignment. It does not cover scaling Reverb across multiple nodes, Redis-backed horizontal scaling, or rotating the generated Reverb secret without downtime.

## Verification

```bash
orbit node:doctor <node>
orbit realtime:show
getent ahostsv4 reverb.orbit
```

On the node itself, `systemctl status orbit-websocket` reports the unit active. `orbit realtime:show` reports a configured connection at `wss://reverb.orbit` once the role is active; `getent ahostsv4 reverb.orbit` resolves to the role's node address over WireGuard. `orbit realtime:tail` and the header of `orbit top` go live against real record changes once both report configured. From a node that trusts the Orbit CA, `curl -i https://reverb.orbit/apps/<app-id>/events -X POST` should answer `401 Unauthorized` with `Authentication signature invalid` rather than a connection or TLS error, confirming the Pusher-protocol server is live behind the role's Caddy site.
