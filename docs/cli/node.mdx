A Node is a machine that the Gateway manages over SSH and reaches over WireGuard. The `node` family provisions a machine, converges it again after a change, changes the unique registry name, assigns and removes roles, records which Node may call which, and sets the apps root.

The [Node provisioning](/reference/node-provisioning), [Node settings](/reference/node-settings), and [Node retarget](/reference/node-retarget) references own the bootstrap identity, the storage contract, and the public SSH boundaries that these commands follow.

## Commands

| Command | Result |
| --- | --- |
| [`node:add`](#orbit-nodeadd) | Provision a new machine or converge an existing Node. |
| [`node:list`](#orbit-nodelist) | List Nodes registered with the active Gateway. |
| [`node:show`](#orbit-nodeshow) | Show one Node. |
| [`node:metrics`](#orbit-nodemetrics) | Show one synchronous metrics snapshot for a Node. |
| [`node:remove`](#orbit-noderemove) | Remove a Node and restore its public SSH recovery rule. |
| [`node:rename`](#orbit-noderename) | Change the unique registry name of one Node. |
| [`node:role:add`](#orbit-noderoleadd) | Add or converge one role assignment. |
| [`node:role:list`](#orbit-noderolelist) | List the role assignments of one Node. |
| [`node:role:relocate`](#orbit-noderolerelocate) | Move a relocatable singleton role (`gateway`, `websocket`, or `metrics`) to another Node. |
| [`node:role:remove`](#orbit-noderoleremove) | Remove one role assignment and its dependent state. |
| [`node:access:add`](#orbit-nodeaccessadd) | Allow one Node to run commands on another Node. |
| [`node:access:remove`](#orbit-nodeaccessremove) | Remove one access edge. |
| [`node:settings`](#orbit-nodesettings) | Update the typed storage settings of one Node. |

Every command accepts `--json`. Commands that take a `node` argument or `--node` option accept the numeric Node ID; `node:rename`, `node:role:*`, and `node:settings` also accept the registered Node name.

Node and role lists use read-only tables with every column retained at narrow widths. Below the minimum table width, each row becomes a labeled record. Empty lists say `No nodes.` or `No roles.`. Node details use an aligned tree; absent human values use an em dash, and TLDs include their leading dot. JSON retains the existing fields and null values.

Requests show an indeterminate progress tree while the Gateway works. The CLI does not receive individual provisioning steps. It settles the operation before showing its result or error and request ID. Piped output keeps readable waiting and settled results without animation; JSON contains only the response.

Arguments and settings remain explicit in every mode. Removal confirmations default to No and identify the target and effect. Declining, cancelling, or reaching end of input exits 1 before removal. Automation, including JSON, requires the existing `--force` consent option. `--offline` and `--purge-data` do not supply consent.

## orbit node:add

Add a machine to the fleet. The same command provisions a new machine and converges an existing Node after you change its TLD, roles, or settings.

```bash
orbit node:add <name> [host] [options]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `name` | yes | Unique registry name. Change it later with [`node:rename`](#orbit-noderename). |
| `host` | no | Public SSH host. Required for a new machine. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--ssh-port=PORT` | `22` | Public SSH port. |
| `--user=USER` | `root` for a new Node, the managed user for an existing Node | Bootstrap SSH user. Name one when the host allows no root login or the managed user cannot log in. |
| `--orbit-user=USER` | `orbit` | Orbit-managed system user that every later Gateway command runs as. |
| `--platform=PLATFORM` | `linux` | Node platform. Only `linux` is accepted. |
| `--architecture=ARCH` | observed on the machine | Machine architecture such as `x86_64` or `aarch64`. A new Node records the observed value, and an explicit value must equal it. |
| `--tld=TLD` | none | Node TLD. Generated development Route domains use it when no active Cluster TLD owns the Node. Production clone previews still use the Node TLD. |
| `--role=ROLE` | none | Initial role assignment. Repeat the option for more than one role. |
| `--host-key-fingerprint=SHA256` | none | Approved SSH host key fingerprint. |
| `--cluster=ID` | none | Numeric Cluster ID to join. |
| `--wireguard-ip=IP` | generated | Stable WireGuard IP address. |
| `--lan-ip=IP` | none | Cluster-local LAN IPv4 address that a Router uses to reach this Node. |
| `--wireguard-endpoint=HOST:PORT` | generated | Per-node WireGuard endpoint override. See [WireGuard endpoints](/reference/wireguard-endpoints). |
| `--dns-server=IP` | Orbit VPN DNS | Per-node DNS server override. See [Private DNS](/reference/private-dns). |
| `--setting=PATH:VALUE` | none | Repeatable typed Node setting. The only setting path is `apps.path`. |

The Gateway opens one SSH session as the bootstrap user, installs the base packages, creates the managed user, and then verifies SSH as that user. Bootstrap opens the `orbit:public-ssh-recovery` firewall rule; the first role convergence closes public SSH again, so a Node provisioned with roles ends reachable only over WireGuard.

Provision an app-dev machine with its own TLD and apps root:

```bash
orbit node:add beast beast.example.com \
  --role=app-dev \
  --tld=test \
  --setting=apps.path:/srv/orbit/apps
```

Converge an existing Node after adding a role:

```bash
orbit node:add beast --role=app-dev --role=database
```

<Note>
A production Node that receives clones needs `--tld`; the [instance:clone](/cli/instance#orbit-instanceclone) command derives its preview domain from that value.
</Note>

The roles you can assign are `app-dev`, `app-prod`, `router`, `ingress`, `database`, `metrics`, `websocket`, `gateway`, and `vpn`. The [Database role](/reference/database-role) and [Metrics](/reference/metrics) references list which roles may share one Node. The `websocket` role runs Reverb for realtime events and has no role conflicts, so it combines with `gateway` today. Move `websocket` or `metrics` with [`node:role:relocate`](#orbit-noderolerelocate); see [Realtime events with Reverb](/solutions/realtime-reverb). The `gateway` role is a singleton you can relocate without moving `vpn`; see [Relocate the gateway role](/solutions/relocate-gateway-role). `vpn` stays protected from generic add and remove.

## orbit node:metrics

Show one synchronous metrics snapshot for a Node: per-core CPU, memory, swap, load averages, uptime, pressure, and disks.

```bash
orbit node:metrics <node> [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | Numeric Node ID or registered Node name. |

```bash
orbit node:metrics beast
```

The Gateway reads the snapshot from the [Metrics role's](/reference/metrics) own Prometheus, through the same Grafana datasource proxy `metrics.orbit` uses to serve dashboards: it authenticates with the stored Grafana credential, resolves the Prometheus datasource, and runs one instant PromQL query per metric group (cores, memory and swap, load and uptime, pressure, disks), filtered to this Node's exporter instance (`WireGuardIP:9100`). No software needs to run on the Node itself beyond the Metrics role's own `prometheus-node-exporter` unit, and the Gateway never stores a sample. The Gateway answers `node.metrics_unavailable` (HTTP 422) for a Node that is not active or has no WireGuard address, `metrics.assignment_missing` (HTTP 409) when no Node carries the Metrics role, and `node.metrics_unreachable` (HTTP 502) when Grafana could not be read or Prometheus has no samples yet for this Node's exporter.

The snapshot reports `cores` as a list of per-core busy ratios from 0 to 1, `memory` and `swap` as used and total bytes, `load` as the 1, 5, and 15-minute averages, `uptime_seconds`, `pressure` as the `some` `avg10` value from each of CPU, memory, and I/O pressure (`0` when the Node's kernel has no PSI support), and `disks` as a list of mount, used, and total bytes, with pseudo filesystems (`tmpfs`, `proc`, `sysfs`, and similar) excluded and `/` listed first. Human output renders bytes and durations in readable units; JSON keeps the raw numbers.

The [web app](/reference/web-app) reads the same Prometheus data directly from the Metrics role's Grafana, for every Node at once, rather than calling `node:metrics` per Node; see [ADR 0088](/decisions/0088-cli-reads-display-metrics-from-grafana).

## orbit node:remove

Remove a Node record and its Gateway-side projections. The Gateway restores the public SSH recovery rule and leaves the machine reachable on its recorded public SSH target so you can provision it again.

```bash
orbit node:remove <node> [--force] [--offline] [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | Numeric Node ID. |

| Option | Meaning |
| --- | --- |
| `--force` | Skip the confirmation prompt. Required with `--offline`. |
| `--offline` | Shed roles on the Gateway side and remove a Node that the Gateway cannot reach. The Gateway probes the Node first; a Node that answers keeps every ordinary guard. |

The Gateway refuses the request while the Node still owns Instances, legacy instances, firewall rules, roles, or Processes. It never removes the Gateway or VPN Node, or the Node that sends the request.

```bash
orbit node:remove 7
orbit node:remove 7 --offline --force
```

<Warning>
`--offline --force` changes nothing on the machine. Caddy sites, checkouts, containers, units, and UFW rules stay in place, public SSH stays closed, and the response lists what remains under `retained_on_node`.
</Warning>

The [Node provisioning reference](/reference/node-provisioning#remove-a-node) lists each removal step and failure code.

## orbit node:rename

Change the unique registry name of one Node. The name is not WireGuard peer material. Keys, addresses, SSH identity, and role assignments stay on the same Node.

```bash
orbit node:rename <node> <name> [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | Node ID or registered name. |
| `name` | yes | New unique registry name. ASCII letters, digits, dashes, and underscores. Maximum 63 characters. |

A request that repeats the current name succeeds and writes nothing. The Gateway holds the provisioning lock for the current name and then for the new name so a concurrent `node:add` cannot claim the destination.

```bash
orbit node:rename gateway vpn
```

Rename the current `gateway` Node to `vpn` before you register a new VPS as `gateway`. [Relocate the gateway role](/solutions/relocate-gateway-role) owns that cutover order. [ADR 0091](/decisions/0091-rename-a-node-without-changing-wireguard-identity) owns the command.

## orbit node:role:add

Add one role assignment to a Node, or converge an existing assignment again.

```bash
orbit node:role:add <node> <role> [--converge] [--postgres-process=ID] [--clickhouse-process=ID] [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | Node ID or registered name. |
| `role` | yes | Role name. |

| Option | Meaning |
| --- | --- |
| `--converge` | Re-run convergence for an assignment that is active, whose failed step starts with `converge:`, or that has stayed `provisioning` for 11 minutes, the role lock's request term plus a 1-minute margin, while no operation holds the Node's role lock. |
| `--postgres-process=ID` | For `analytics` only: the PostgreSQL 16 Process on a database Node that holds the Plausible accounts. |
| `--clickhouse-process=ID` | For `analytics` only: the ClickHouse Process on a database Node that holds the events. |

```bash
orbit node:role:add beast database
orbit node:role:add beast metrics --converge
orbit node:role:add services analytics --postgres-process=41 --clickhouse-process=42
```

The `analytics` role needs both Process options. In a terminal the command lists the Docker Processes that run the right image and asks you to pick each one you left out; with `--json` or `--no-interaction` it refuses. The [Analytics role](/reference/analytics) page owns what the role runs and publishes.

The command refuses a role that conflicts with one the Node holds, before it converges anything, with `validation.failed` and `Role [ingress] conflicts with assigned role [gateway].`. For example, `ingress` never runs on the Gateway Node. [Role compatibility](/reference/node-provisioning#role-compatibility) lists every conflicting pair.

Role operations on one Node run one at a time, as [Node provisioning](/reference/node-provisioning#role-operations-on-one-node) describes. A command that waits too long fails with `node_role.convergence_failed`, `details.step` `converge:node-lock`, and `details.error_code` `node_role.node_busy`, and leaves the assignment as it was; run it again. Human output prints the step and the error code under the message.

A convergence step that does not fail the role still reports its failure. The role stays `active`, and `follow_up` in the response names what failed and how to retry it. The command prints it as a warning after the result. Today only the `gateway` role's [private DNS route](/reference/private-dns#the-gateway-machine) reports this way, on `node:role:add` and on `node:role:relocate`.

`gateway`, `websocket`, and `metrics` are mutable singletons. Prefer [`node:role:relocate`](#orbit-noderolerelocate) when the assignment already exists. Adding `gateway` grants directed access from that Node to the active `vpn` node and the active `metrics` node when those nodes exist and are not the Gateway itself. `vpn` is refused.

## orbit node:role:relocate

Move a relocatable singleton role (`gateway`, `websocket`, or `metrics`) from its current Node onto the named Node. The command keeps one active assignment for the whole request.

The target must not hold a conflicting role. `gateway` is refused onto a Node that holds `ingress`, `app-dev`, `app-prod`, `database`, or `analytics`, with `validation.failed` and `Role [gateway] conflicts with assigned role [ROLE].`.

```bash
orbit node:role:relocate <node> <role> [--from] [--force] [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | Node ID or registered name of the target. |
| `role` | yes | `gateway`, `websocket`, or `metrics`. |

| Option | Meaning |
| --- | --- |
| `--from` | Optional source Node ID or name. Omit to use the current holder. Required to reconcile leftovers when the target already holds the role. |
| `--force` | Confirm the transfer. Required in JSON and other non-interactive modes. |

For `gateway`, the Gateway opens the gateway HTTPS firewall on the target, transfers the assignment, grants the new Gateway access to the `vpn` and `metrics` nodes, republishes private DNS on the `vpn` node, and adds the [private DNS route](/reference/private-dns#the-gateway-machine) on the target. It then removes that route from the source and retracts that firewall there. A failed target route does not stop the move, and the command prints its `follow_up` as a warning. A failed source removal leaves the move incomplete, and the error names the `--from` command that finishes it. The target must not already hold `app-dev`, `app-prod`, or `database`. Relocate does not move `vpn`, stop Caddy or PHP-FPM on the source, or copy the serving checkout. After the split, `node:add` and peer converge install hub WireGuard credentials on the `vpn` node, not on the Gateway PHP host. [Relocate the gateway role](/solutions/relocate-gateway-role) owns ordering, the leftover serving stack, and CLI profile updates. The granted access set is `vpn` and `metrics`.

For `websocket` and `metrics`, relocate copies missing role-owned credentials onto the target, transfers the assignment, converges the target baseline, and retracts the source publication and runtime. It does not overwrite credentials the target already has. When the target already holds the role, pass `--from` to move leftover source resources and retract that Node. When converging the target or retracting the source fails, the role already runs on the target. The command then fails with its usual error code, the failing step's own code in `details.error_code`, such as `metrics.docker_unavailable`, `details.step` set to `converge:STEP` on the target or `remove:STEP` on the source, and a message that the move is incomplete and names the `--from` command that finishes it once the source Node is reachable. A relocation reconciles Metrics once, after the source is retracted, so a slow Metrics Node never holds the source retraction. The move is complete by then, so a failed Metrics reconcile does not fail the command: it succeeds with a warning in `follow_up` that names the Metrics Node and the `orbit node:role:add <metrics-node> metrics --converge` command that reconciles it.

```bash
orbit node:role:relocate beast gateway --force
orbit node:role:relocate services websocket --force
orbit node:role:relocate services websocket --from beast --force
```

## orbit node:role:remove

Remove one role assignment from a Node. Removing the last role restores the public SSH recovery rule before the Gateway deletes the assignment.

```bash
orbit node:role:remove <node> <role> [--force] [--purge-data] [--offline] [--json]
```

| Option | Meaning |
| --- | --- |
| `--force` | Confirm destructive role removal and dependent cleanup. |
| `--purge-data` | Request supported role-owned data cleanup. For `metrics`, this deletes the Prometheus and Grafana volumes and stored credentials. For `websocket`, this deletes the Reverb checkout at its install path. |
| `--offline` | Remove the role from a Node the Gateway cannot reach. |

```bash
orbit node:role:remove beast database --force
```

A role that still hosts a Route target, such as `app-dev` or `app-prod` with active Instances, is refused until those Instances are removed.

When two removals of the same role run together, the second waits for the Node's role lock. If the first removed the role meanwhile, the second fails with `node_role.already_removed` (409) and changes nothing. A role the Node never had returns `http.404`.

The command removes a role that is `active`, or `failed` after a convergence (`failed_step=converge:STEP`) or an earlier removal (`failed_step=remove:STEP`). Each removal step repeats safely over what a failed convergence left behind: on a Node that never received Caddy or Docker, the Caddy build and the Metrics container cleanup find nothing to remove. A role that is still converging or being removed is refused until it has stayed `provisioning` or `removing` for 11 minutes, the role lock's request term plus a 1-minute margin, and no operation holds the Node's role lock. A failed removal leaves the role `failed` with `failed_step=remove:STEP` and returns the step's own code in `details.error_code`. A Caddy build failure on `ingress` uses `details.step` `remove:caddy-config` and `details.error_code` `ingress.caddy_config_failed`. [Caddy configuration](/reference/caddy-configuration#when-a-build-fails) describes the codes and the message. Run the same command again.

## orbit node:access:add

Allow one Node to run Gateway commands on another Node. Access edges authorize Orbit commands and Gateway API actions; they do not change private network reachability, which WireGuard membership already grants. Adding or relocating the `gateway` role creates the Gateway → `vpn` and Gateway → `metrics` edges automatically.

```bash
orbit node:access:add <consumer> <serving> [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `consumer` | yes | Numeric ID of the Node that sends commands. |
| `serving` | yes | Numeric ID of the Node that receives them. |

```bash
orbit node:access:add 3 7
```

## orbit node:access:remove

Remove one access edge from the active Gateway.

```bash
orbit node:access:remove <consumer> <serving> [--force] [--json]
```

| Option | Meaning |
| --- | --- |
| `--force` | Skip the confirmation prompt. |

## orbit node:settings

Update the typed storage settings of one Node. The only setting path is `apps.path`, the root under which the Gateway creates Instance checkouts.

```bash
orbit node:settings <node> --setting=apps.path:/mnt/apps [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | Node ID or registered name. |

| Option | Meaning |
| --- | --- |
| `--setting=PATH:VALUE` | Repeatable setting. The CLI splits at the first colon, so a value may contain more colons. An empty value unsets the setting: `--setting=apps.path:`. |

The command requires at least one `--setting` option. Changing the apps root does not move, rewrite, or delete an existing checkout; the [Node settings reference](/reference/node-settings) lists the validation and failure codes.
