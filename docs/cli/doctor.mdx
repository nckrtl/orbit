Doctor is one command. The Gateway compares its stored intent with a bounded, read-only observation of each Node and returns one report. Doctor never converges, installs, removes, starts, stops, restarts, adopts, or otherwise changes managed state.

## Commands

| Command | Result |
| --- | --- |
| [`doctor`](#orbit-doctor) | Verify registered Node state without making repairs. |

The command accepts `--json`.

## orbit doctor

Verify one Node or every Node the caller may address, optionally limited to a set of families.

```bash
orbit doctor [--node=ID] [--family=FAMILY ...] [--json]
```

| Option | Default | Meaning |
| --- | --- | --- |
| `--node=ID` | every registered Node the caller may address | Numeric Node ID. The CLI rejects a value that is not a positive integer with `doctor.node_id_invalid`. |
| `--family=FAMILY` | every family | Limit checks to one family. Repeat the option for more than one. Accepted values are `node`, `role`, `app`, `instance`, `schedule`, `tool`, `process`, `firewall`, `database_connection`, and `route`. The Gateway refuses another value with `validation.failed`. |

```bash
orbit doctor
orbit doctor --node=7 --family=instance --family=process
orbit doctor --family=firewall --json
```

Human output shows a progress indicator while the request runs. Then it shows a table with the columns Node, Family, Status, Checked, Resource, and Finding. A family without findings has one row, with "—" in the last two columns. A family with findings has one row for each finding. The Resource column names the resource type and name, so findings with the same code stay distinct. The Finding column shows the code, the summary, and the expected and observed values. The last lines give the report's summary counts (Nodes, families, checks, drift, and unverifiable), whether the fleet is healthy, and the request ID. JSON output returns the same report, including the same `summary` counts, as one document.

The exit status follows the report.

| Exit status | Meaning |
| --- | --- |
| `0` | Every selected Node and family is healthy. |
| `1` | At least one finding is drift or unverifiable, or the Gateway could not be reached. |

The Gateway answers a completed report with HTTP 200, also when it holds drift or unverifiable findings. Transport and authorization failures use the normal error envelope.

<Note>
Doctor selects only Nodes that the caller may address through an access grant. The Gateway refuses a `--node` value outside that set with `node_access.required`, so Doctor never inspects a Node that the caller could not otherwise reach.
</Note>

### How the Gateway inspects

The Gateway observes each Node once over SSH before it runs the family probes. The observation holds reachability, platform, architecture, and whether the WireGuard address is present. It also holds the [Node agent](/reference/node-agent#doctor) binary, unit, state, and checksums.

A failed SSH command makes the Node unreachable, and the `node` family reports `node.ssh_unreachable`. A malformed or truncated observation makes the `node` family report `node.inspection_failed` instead. In both cases the other families treat the Node as unreachable. Database-only checks still run: Node and role lifecycle, role conflicts, Route status, and database connections. Each other family with resources on that Node reports one `*.node_unreachable` issue instead of its checks. The `role` family does this only when the Node has an active role. The `route` family does this only when the Node serves a custom proxy Route.

Checks that read root-owned files run through passwordless `sudo` on the Node. Every check that reads the live Caddyfile is one of them, because Orbit publishes each Caddyfile version under `/etc/caddy/orbit-versions` as `root:caddy` with mode `0750`.

Families run in this order, whatever filter you pass: `node`, `role`, `app`, `instance`, `schedule`, `tool`, `process`, `firewall`, `database_connection`, `route`. Nodes sort by name and then ID. Resources sort by ID. So two runs against the same state produce the same report.

Each issue carries a stable code, a kind of `drift` or `unverifiable`, the resource type, ID, and name, a summary, and bounded `expected` and `observed` values. A family is `healthy` with no issues, `drift` with drift only, and `unverifiable` when any issue is unverifiable. `checked` counts the family's persisted resources on that Node, not commands. A family without resources on the Node is `healthy` with `checked` 0.

The report never contains raw output, commands, paths, URLs, branch names, repository origins, credentials, setting values, private keys, environment values, configuration contents, or exception text. A Route issue names the Route's domain as its resource name.

The `app` and `instance` families compare the `remote.origin.url` value stored in each checkout. They ignore `insteadOf` rewrites from the Node's Git configuration, so a Node that rewrites HTTPS URLs to SSH still matches. The `app` family looks for a development checkout under the Node's [apps root](/reference/node-settings#derive-the-effective-root).

For a development Instance, `instance.source_identity_mismatch` means the checkout does not hold the recorded history: the recorded starting commit is missing, or `HEAD` shares no history with it. A checkout on another branch, on a detached `HEAD`, or reset below the starting commit is normal development work, not drift. Commands that act on the recorded branch check it when they run. For example, `instance:destroy` refuses a checkout on another branch with `instance.source_branch_mismatch`.

The `tool` family compares only desired intent. A Tool without a version constraint needs only to be installed. With a constraint, Doctor checks the normalized installed version against it and reports `tool.version_mismatch` when the constraint rejects it. An invalid stored constraint, or a version that Doctor cannot normalize, reports `tool.inspection_failed`. Doctor never compares the version with the Tool's `installed_version`, because that field records the last operation's result, not intent.

Every Instance is expected to be `active`, except a task workspace that is not visitable. That workspace has no Route, so its expected final state is `source_resolved`; the [tasks reference](/reference/tasks#shared-instance) owns that rule. A non-null provisioning step is unfinished unless it is the terminal `active` or `clone-completed` step. A lifecycle state before the Instance's settled state is also still provisioning. A non-null `failed_step` reports immediately; Doctor skips other unfinished provisioning while its row has changed within the last 20 minutes, and older provisioning reports only `instance.provisioning_stuck`. The `app` probe also excludes provisioning Instances; only the `instance` family reports when provisioning becomes stuck. A state later than the settled state is unexpected and reports `instance.lifecycle_not_active` with the expected state. The `instance` probe skips an Instance already in `removing`, except that removal lasting 10 minutes or more reports `instance.removal_stuck`; it also drops issues if removal starts or the row is deleted during inspection. The `app` probe excludes removing and unfinished-provisioning Instances when selecting eligible checkouts. The `process` probe skips Processes whose Instance is removing, and drops findings if removal starts or the Instance is deleted during inspection. The `database_connection` probe skips attachments whose Instance is removing, including when it rereads the attachment after inspection. No other family has a general removing-Instance skip. An unreachable Node skips the Instance lifecycle checks.

A role assignment that has stayed `provisioning` or `removing` for 11 minutes, while no operation holds the Node's [role lock](/reference/node-provisioning#role-operations-on-one-node), reports `role.claim_stale` instead of `role.lifecycle_not_active`: the operation that claimed it stopped without finishing, for example because its Gateway worker was killed. 11 minutes is the role lock's 10-minute request term plus a 1-minute margin. The lock itself ends at most one [term](/reference/node-provisioning#lock-renewal) after the operation's last command started, so a killed worker blocks the role for at most that term plus the 1-minute margin. `orbit node:role:add <node> <role> --converge` converges a stale `provisioning` claim again, and `orbit node:role:remove` removes a stale claim of either kind.

Every Route is expected to be `active`. Any other status reports `route.lifecycle_not_active` on the Node that serves the Route; the [routes reference](/reference/routes#check-route-status-with-doctor) says which Node that is.

An `ingress` role needs Caddy running on its Node, because the Node's Caddy serves its public sites. Doctor reports `role.services_inactive` when Caddy is stopped and `role.firewall_projection_mismatch` when the Ingress public HTTP rules differ.

A sleeping development Instance is not drift. When the awake marker is absent, Doctor does not report `process.state_mismatch` for a Process that is desired running, not keep-alive, and observed stopped; the [hibernation reference](/reference/app-dev-runtime-hibernation#inspect) owns that rule. A prepared production home without a `current` link is healthy before its first deployment; the [release layout reference](/reference/deployments#inspect-release-placement-with-doctor) owns that rule.

The reference pages describe each family's comparison in more detail: [Schedules](/reference/schedules#inspect-schedule-drift), [Tools](/reference/tools#check-removal-with-doctor), [Database connections](/reference/database-connections#inspect-attachments-with-doctor), [Instance environment variables](/reference/environment-variables#inspect-the-projection-with-doctor), [custom proxy Routes](/reference/routes#custom-proxy-routes), [the Caddy release a role needs](/reference/node-provisioning#package-sources), and [Caddy build drift](/reference/caddy-configuration#check-a-node-with-doctor).

<Warning>
Doctor keeps no report history. The Gateway writes one ordinary Activity row for the request and stores no findings, so keep the returned report and request ID if you need them later.
</Warning>

## Why it works this way

These reasons explain the design. Check them before you propose a change.

### Verify only

Doctor reports drift and never repairs it. A second convergence engine would compete with the commands that own each change. So Doctor uses only database reads and read-only commands. Its inspectors stay separate from the managers that change Nodes, and Doctor never calls a mutating manager or action. Code that both sides need, such as a catalog, a parser, or a renderer, moves to a shared place. Repair stays with those commands, such as `node:role:add --converge`. Restore, adoption, interactive repair, and scans for unmanaged host state are outside Doctor.

### No stored reports

Doctor keeps no reports, findings, or raw observations. The request's one Activity row is its only write. Stored raw output could expose paths, configuration, or credentials.

### One observation per Node

One bounded observation limits remote work. Every family then uses the same reachability and identity facts for that Node.

### A closed family list

Each family is an explicit probe with its own issue codes, order, and tests. There is no plugin registry. An architecture test requires each Gateway model to be a checked resource, a typed input, or excluded. A new model fails that test until its Doctor role is explicit.

### Bounded values

Issue values are booleans, enums, normalized versions, or fixed labels. This keeps secrets and diagnostic data out of the report. An unknown internal code becomes the family's `*.inspection_failed` issue.
